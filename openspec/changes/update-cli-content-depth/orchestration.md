# Порядок делегации и проверки

## Перед началом

Прочитать proposal, design, spec deltas, TASK_CONTRACT, verification, tasks и фактические AGENTS.md. Убедиться, что пользователь согласовал M1. Не начинать M2 и не создавать goal без явного запроса. Запрос из GOAL_PROMPT предназначен для последующего пользовательского запуска.

Рабочее дерево содержит пользовательские изменения: не включать их в чужой коммит, не откатывать и не выполнять reset/clean ради чистоты. Все журналы/рабочие копии — `.learning`, никакого auth и личного лога в исходники. Незавершённое предыдущее предложение не архивировать автоматически.

## Гранулярность

Выполнять T01–T06 последовательно; не поручать одному developer весь change с одним неограниченным ревью. Контракты уже созданы штатным init-contract и сохранены в contracts. Их status FROZEN означает фиксированные границы, не разрешение на реализацию и не PASS.

Тексты обязательных сценариев берутся из spec deltas; дополнительные конечные проверки и fixtures — из verification.yaml. Если check_content_contract ещё не реализован, batch не может пройти через отсутствие команды: T01 обязан реализовать свой stage и интерфейс, последующие batch добавляют только свои проверки.

Программный TASK_CONTRACT — M1 в целом. Task_id batch сохраняется через все попытки. Run IDs и SHA меняются; task_id не меняется, чтобы сбросить ledger/счётчик раундов.

Границы промежуточного PASS заданы `batches[].scope_note` и `scoped_acceptance_criteria` в verification.yaml. Например, T02 проверяет восемь уже созданных схем, а не отсутствующие на этом этапе D09–D12. T06 повторно проверяет все двенадцать. Это заранее определённая поэтапная приёмка, не разрешение переносить обязательную работу в follow-up. При отсутствии собственного критерия в контракте нельзя расширять его по общему тексту программного AC.

## Изолированное состояние convergence

Штатный helper пишет в `$CODEX_HOME/state`. Для него использовать **только локальный** `.learning/convergence`, не глобальный профиль. Перед отдельным вызовом сохранить старый CODEX_HOME, временно назначить локальный, восстановить в finally. Это состояние helper, не авторизованный Codex-профиль; запуск модели с ним не предполагается.

Перед первым запуском batch убедиться, что локальный contract совпадает по SHA-256 с tracked contracts/Txx/TASK_CONTRACT.yaml. Если состояние отсутствует, восстановить ровно сохранённый контракт; существующий отличный контракт не перезаписывать --force. При передаче reviewer приложить абсолютные пути frozen документов; не предполагать, что его broker наследует environment shell helper.

## Вход developer

Передать: task_id, batch, абсолютные contract/spec/design/verification пути, baseline SHA, allowed files, блокеры ledger при повторе, критерий завершения и запреты. Developer не один в репозитории; сохраняет чужие правки и согласует свой diff с фактическим деревом.

Обязанности: TDD для изменяемой логики; tests-red перед исправлением и fresh tests-green; документация/схема по rubric; минимум изменений в пределах batch. Не исправлять соседние идеи без frozen basis, не менять ожидание независимого теста ради PASS, не ставить зависимости в offline. Новые тесты проверяют реальные регрессии, а не одно наличие строки.

Выход: commit SHA, ограниченный diff, команда/exit каждого запуска, относительные evidence paths и SHA-256, сценарные результаты, закрытые инварианты и явные ограничения. Коммит только собственных файлов; если commit невозможен, честно передать причину — review-sha нельзя выдумывать.

## Preflight и вход reviewer

Оркестратор выполняет `python C:\Users\Mi\.codex\scripts\convergence_tools.py preflight --repo-path <absolute_repo> --review-sha <SHA>`; ошибки упаковки/preflight — REVIEW_INFRA_ERROR, не новая реализация и не продуктовая находка. Отсутствие обязательного runtime/test prerequisite — отдельная проблема среды; не исправлять её отключением проверки.

Reviewer получает task_id, точный SHA, frozen contract, verification, applicable ADR/spec, scope diff, тестовые доказательства и текущий ledger. Режим первого прохода INITIAL_REVIEW; следующие FIX_VERIFICATION, только открытые находки и регрессии fix diff. POST_ARBITRATION_VERIFICATION ограничен closure_tests.

Reviewer выполняет независимый review содержания и кода, проверяет свежесть доказательств и при необходимости воспроизводит конечные сценарии. Только он использует broker_health/review_submit/review_wait. Наличие общей справки, заголовка, фикстуры или слова не подтверждает функцию. Не добавлять новые требования/платформы/SDK за пределами frozen scope.

Формат ответа:

```yaml
task_id: codex-cli-content-depth-v1-t01
review_sha: <реальный SHA>
review_mode: INITIAL_REVIEW
verdict: APPROVE | REQUEST_CHANGES | REVIEW_INFRA_ERROR
scenario_results:
  - id: INV-01
    status: PASS | FAIL | BLOCKED | NOT_RUN
    evidence: <путь и хеш>
findings:
  - id: REV-001
    severity: P1
    acceptance_criterion: AC-1
    scenario_id: INV-01
    blocking_basis: VIOLATES_FROZEN_AC
    location: <абсолютный путь и строки>
    counterexample: <воспроизводимые вход и наблюдаемый отказ>
    required_invariant: <что обязано сохраниться, не архитектурный совет>
```

## Ledger и решение

Ledger ведёт только оркестратор: finding_id, severity, basis, AC/scenario, evidence, introduced_sha, status, closure_evidence/deferred_ticket. P0/P1 с нарушением frozen AC, данных, безопасности или с регрессией — OPEN до доказанного закрытия. Настоящий блокер нельзя понизить без конкретного опровержения. P2/P3 — отдельные follow-up; дубликаты/вне scope — REJECTED с причиной.

Отсутствующий обязательный тест или rubric-пункт заносится блокером даже при пустом списке broker. Ноль находок сам по себе не доказывает выполненные AC. Batch принимается после PASS его обязательных сценариев и нуля OPEN P0/P1; sensor REQUEST_CHANGES из-за deferred P2/P3 не требует повторного review неизменённого SHA.

## Пределы review-loop

Для этого change установлен предел **три обычных раунда на batch суммарно**, включая INITIAL_REVIEW: раунд 1 — INITIAL_REVIEW, раунды 2 и 3 — FIX_VERIFICATION. Сохранять open_before/open_after после каждого завершённого ревью. Если после третьего обычного раунда остаётся хотя бы один настоящий P0/P1, оркестратор переходит к арбитражу независимо от уменьшения числа находок: четвёртое обычное ревью запрещено. Это конкретизация более общего convergence-протокола, а не три дополнительных fix-раунда после initial.

После каждого обычного раунда записать его в ledger штатным ledger-record-round и вызвать convergence-check. При трёх записанных раундах с открытыми блокерами helper возвращает 2; оркестратор запускает arbitrate и фиксирует CLOSURE_PLAN.yaml: выбранная сохраняющая контракт архитектура, конечные изменения, точные closure_tests, deferred/rejected, max_post_arbitration_rounds: 2, subcase_expansion_prohibited: true. Сгенерированные helper заглушки вида «Automated test pinning ...» заменить точными тестами и командами до замораживания плана и передачи developer.

При существующем CLOSURE_PLAN состояние POST_ARBITRATION имеет приоритет над обычным счётчиком. **Повторно вызывать arbitrate нельзя:** он может перезаписать план и обнулить post_arbitration_round. Перед каждой из двух разрешённых post-проверок убедиться, что счётчик меньше 2, затем вызвать post-arb-round ровно один раз и сохранить review_id/SHA/результат. На счётчике 2 третье post-ревью запрещено, даже если helper позволяет ещё раз увеличить число. Один exit code 0 convergence-check не означает APPROVE: он также используется для IN_PROGRESS; решение дополнительно проверяет ledger, обязательные сценарии и текущую фазу.

Таким образом, одна задача имеет максимум **пять содержательных ревью: три обычных и два post-arbitration**. Повтор по неизменённому SHA, обнуление task_id/ledger/счётчика или новое имя той же задачи не разрешены. Ошибка инфраструктуры не считается содержательным ревью, но не даёт права повторно отправить уже FINAL SHA или бесконечно ремонтировать окружение.

После арбитража новые subcases запрещены. Первый проход проверяет только closure_tests; при провале допускается одна корректировка и один последний проход. Далее — окончательное решение без новых циклов: либо fallback, сохраняющий AC, либо незакрытый обязательный результат с отдельным следующим тикетом и остановкой текущих попыток. Audited warning **не делает проваленный AC успешным** и не позволяет отметить M1 достигнутым. Так соблюдаются одновременно hard-stop и честная приёмка.

На пятом суммарном раунде дополнительно применяется обязательная реструктуризация: слишком крупная задача выделяет prerequisite и минимальную реализацию; конфликт требований получает обязательное архитектурное решение; ошибка инструмента — REVIEW_INFRA_ERROR и ограниченный ремонт инфраструктуры. Это не обнуляет ledger или счётчик и не разрешает удалить исходные обязательные AC.

При слишком крупном batch разрешено выделить prerequisite как отдельный контракт без удаления исходных AC; итог родительского batch остаётся открытым до их выполнения. Не спрашивать пользователя о технической архитектуре, если выбор можно сделать внутри frozen ADR. Требуемые аккаунты, модельный доступ или права среды нельзя выдумывать: сообщить конкретную потребность, не превращать её в архитектурный спор.

## Остановка и итог

Работая в /goal, следовать его состоянию: не отмечать complete при FAIL/BLOCKED/NOT_RUN/SKIP обязательного M1. Для tool-статуса blocked соблюдать глобальное правило трёх последовательных goal-ходов с тем же непреодолимым препятствием; до этого сохранять прогресс и не устраивать polling-loop. Непрошедшая среда фиксируется конкретно, не бесконечной повторной проверкой.

M1 завершается только после T06: все batch приняты, все M1 сценарии PASS, текущий ZIP/evidence совпадает с деревом, native/live ограничения явно показаны. Финальный ответ: SHA, ZIP и отчёты, принятые задачи, deferred follow-ups, статус M1 и отдельный невыполненный M2. Публикация/git push не выполняются.
