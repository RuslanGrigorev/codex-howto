# Валидация функциональности и правила приёмки

## Что означает 100 процентов

**100% требований и сценариев имеют проверки; 100% обязательных проверок выполнены успешно для выпускаемого кандидата.** Это не 100% line coverage и не математическое доказательство отсутствия любых ошибок.

`traceability.json` — полный перечень сценариев этого change. Его поля `planned_check` и `implementation_status: planned` не являются существующими тестами или результатами. До написания кода полнота планирования может быть 100%, а число подтверждённых продуктовых сценариев — ноль.

Пакет спецификации и готовый курс проверяются разными командами. Проверка `tools/check_spec_pack.py` относится только к данному пакету; контракт будущего `scripts/verify.py` приведён ниже.

## Команды продукта, которые нужно реализовать

```bash
# Быстрый полный детерминированный набор без модели и сети.
python scripts/verify.py --profile offline --report .learning/reports/offline.json

# Настоящий Codex; провайдер уже подготовлен. Секреты не передаются аргументами.
python scripts/verify.py --profile live --report .learning/reports/live.json

# Итог по актуальным доказательствам того же кандидата, включая ручной просмотр.
python scripts/verify.py --profile release --evidence-dir .learning/reports --report .learning/reports/release.json

# Режим ученика: одна локальная проверка, без dev-зависимостей.
python scripts/verify.py --exercise small-fix --workspace .learning/workspaces/small-fix
```

Это **контракт будущих команд**, не обещание, что они уже содержатся в этом архиве. `--profile` и `--exercise` взаимоисключающие. Перед записью скрипт проверяет принадлежность пути разрешённому каталогу. Отчёт создаётся даже при сбое предзапуска, когда возможно безопасно его записать.

Коды возврата: 0 — все обязательные проверки выбранного профиля PASS; 1 — FAIL; 2 — BLOCKED/NOT_RUN/недостаточная среда. Тайм-аут не успех. Итог release проверяет все профили, а не только подмножество, выбранное разработчиком.

## Подготовка среды

Точное окружение фиксируется в первом выполненном baseline: Linux x86_64, Python 3.11+, Git, Codex CLI 0.160.0 как начальный кандидат, версии Python-пакетов и браузеров. Python pytest уже используется исходным проектом; Playwright с Chromium и Firefox добавляется только для разработки. Все зависимости и браузеры устанавливаются до изоляции сети. Никакой автоматической установки внутри проверок.

Чтение курса и самостоятельная практика не требуют OpenSpec. Официальный OpenSpec CLI подготавливается заранее для проверки артефактов разработки. Локальная проверка уже установленных инструментов не должна запускать поиск их обновлений.

Живой тест использует один явно заданный доступный провайдер и фиксированное имя модели. Объявленная дополнительная локальная модель требует такого же отдельного прогона с закрытой внешней сетью; до этого её маршрут помечен как непроверенный рецепт, а не поддерживаемая конфигурация. Отсутствие доступа к модели блокирует сертификацию наставника, но не локальную разработку материалов.

## Профиль offline

1. **Структура и данные:** каталог без дублей/циклов; все обязательные файлы, revision и source_id существуют; YAML/TOML/JSON синтаксически валидны; активные Claude-артефакты и явные английские регрессии запрещены. Отдельно проверяется применимость используемого синтаксиса к CLI, поскольку парсер конфигурации этого не доказывает.
2. **Поставка:** проверяется именно распакованный ZIP; локальные URL, файлы примеров, якоря и assets; отсутствие секретов и личных результатов; хеш-манифест; повторная сборка с теми же входами.
3. **Браузер:** оба заявленных браузера запускаются с пустым профилем; учёт всех HTTP(S)/WS запросов; внешняя сеть блокируется на уровне среды теста, не только флагом navigator.onLine. Любая попытка внешнего запроса — нарушение. Для file:// прогоняются все страницы, кнопки, викторины, импорт/экспорт, сброс, отказ storage/clipboard, отключение JS, путь с пробелами и кириллицей.
4. **Практика:** все local-runnable-примеры, эталон и по одной отрицательной мутации на каждое условие. Отдельные тесты проверяют, что ошибка проверяющего кода не приводит к ложному успеху. Ограничение времени процесса и контрольные файлы за пределами рабочего каталога обязательны.
5. **Обновление:** локальные baseline/candidate, удалённая команда, неизвестное изменение, только редакционная правка, повреждённый ответ, отказ сети. Сетевой транспорт в этих тестах заменяется фикстурами; это не выдаётся за проверку доступности реального сайта.

Не требуется одинаковый снимок каждого пикселя. Проверяются наблюдаемые действия, доступность элементов, сообщения и содержимое. Ручной визуальный просмотр остаётся отдельным обязательным результатом.

## Профиль live

Все TUT-сценарии с методом live проходят в реальном Codex трижды, в новых сессиях и копиях упражнения. Это конечный набор регрессионных испытаний, не статистическая гарантия качества модели. Повторный успешный запуск не скрывает предыдущий сбой: все попытки остаются в отчёте; после исправления создаётся новый кандидат и полный актуальный прогон.

Рубрика для каждого применимого диалога: русский язык; верный локальный урок; корректный технический синтаксис; отсутствие нежелательного готового решения; факт реального вызова проверки; честное описание результата; соблюдение области записи; отсутствие ненужного поиска/Docs MCP. Для безопасности и выдачи неподтверждённого зачёта допускается ноль нарушений.

Наблюдаемые файловые эффекты проверяются кодом. Языковой и педагогический смысл рассматривает человек по тем же пунктам; модель не является единственным судьёй собственного успеха. Отказ пользователя от подсказок и явный запрос полного решения рассматриваются раздельно.

Каждый опубликованный `codex-runnable` пример также включается в параметризованный набор: команды, конфигурация, AGENTS.md, skill, MCP, hooks, агент, плагин, сессия и exec — в той мере, в какой курс обещает их исполняемое поведение. Для каждого есть ожидаемый эффект, не только отсутствие ошибки парсера. Не используем `--help` вместо проверки применения конфигурации. Неподдерживаемый пример либо исправляется, либо изменяется спецификация его учебного статуса; молчаливый SKIP запрещён.

Для проверки независимости наставника от документации можно оставить доступ только к выбранному модельному endpoint и закрыть прочие внешние ресурсы. Это **не** называется полностью офлайн-работой модели. Для обещания живого офлайна нужны предзагруженная локальная модель и отдельный полный live-профиль с заблокированным внешним трафиком.

## Ручная проверка

Для каждой записи `method: manual` в матрице проверяющий выполняет её GIVEN/WHEN/THEN и сохраняет результат с `scenario_id`, своим именем/идентификатором, датой, хешем кандидата, наблюдениями и локальным доказательством. Одно общее «всё просмотрел» не заменяет девять отдельных заключений.

Проверяем весь русский маршрут и все десять модулей: язык и терминологию; достижимость цели упражнения; достаточность офлайн-объяснений; правильность технических сведений по сохранённым официальным источникам; границы обещаний для моделей/платформ. Минимум один непрерывный проход полного самостоятельного маршрута в подготовленном окружении без сети обязателен.

## Минимальный JSON-отчёт продукта

Форма результата, не готовое доказательство:

```json
{
  "schema_version": 1,
  "profile": "offline",
  "candidate_tree_sha256": "<хеш файлов кандидата>",
  "spec_sha256": "<хеш спецификации>",
  "environment": {
    "os": "<точная ОС>",
    "python": "<точная версия>",
    "codex": null,
    "provider": null,
    "model": null,
    "browsers": []
  },
  "cases": [
    {
      "scenario_id": "OFF-001-S01",
      "status": "NOT_RUN",
      "check": "<идентификатор выполненной проверки>",
      "evidence": [],
      "message": "Пример формата; проверка ещё не выполнена"
    }
  ],
  "overall": "NOT_RUN"
}
```

В рабочем отчёте placeholders запрещены. `evidence` содержит относительный путь, SHA-256 и тип файла доказательства; перед выпуском проверяются наличие и хеш. Отчёты, рабочие каталоги и генерируемые временные файлы исключены из вычисления хеша проверяемого дерева, чтобы не возникало самоссылки. Исходные спецификации, матрица, код и входы сборки включены. Хеш дерева вычисляется по отсортированным парам «относительный путь + хеш содержимого», а не по времени файлов ZIP.

Статусы: PASS, FAIL, BLOCKED, NOT_RUN, SKIP. Последние четыре не удовлетворяют обязательному сценарию. Ручное подтверждение не может закрыть отсутствующий автоматический тест вместо предусмотренного метода. Тесты live без настоящего провайдера могут иметь полезные локальные фикстуры, но они не закрывают live-строку.

## Gate выпуска

В выпуске должно быть ноль отсутствующих сценариев и ноль устаревших доказательств. Проверка сопоставляет ID, методы, профиль, хеши и результаты; каждая обязательная строка имеет PASS. Все runnable-примеры из каталога также должны иметь актуальный результат. Недостающий браузер, неисправный источник, недоступная модель или незаполненный ручной просмотр блокируют соответствующее обещание/выпуск, а не уменьшают знаменатель процента.

Разрешено разрабатывать и демонстрировать пилот без завершения всего курса, но такой артефакт обозначается пилотом и не называется полной поставкой. Исключение требования оформляется редактированием spec и матрицы с явным обоснованием, а не флагом `--ignore-failures`.

## Что проверено именно в текущем пакете

Фактический результат подготовки спецификации находится в [отчёте подготовки пакета](../../../reports/VALIDATION.md). Продуктовые команды выше и перечисленные в матрице test targets должны быть реализованы по tasks.md. В текущем пакете они не запущены и не представлены как прошедшие.
