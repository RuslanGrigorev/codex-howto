# Техническое решение

## Context

Выбран brownfield-подход: отдельный форк исходного claude-howto, без новой платформы. Проверенные факты об архиве и карта переноса находятся в [migration-map.md](migration-map.md). Поведение задают шесть файлов [specs/](specs/), а не этот документ.

Три границы принципиальны: чтение курса не зависит от модели; самостоятельное упражнение не равно живому запуску Codex; проверка структуры OpenSpec не равна проверке продукта.

## Goals / Non-Goals

Сохраняем Python/Jinja2/Markdown, существующую сборку статического сайта, обычный JavaScript и пригодные тесты. Меняем содержание и необходимые участки кода, а не технологический стек. Все обслуживающие команды работают локально после подготовки зависимостей.

Не вводим сервер приложения, SPA, базу данных, авторизацию, универсальные адаптеры агентов, семантический поиск, фоновый мониторинг релизов и пользовательский менеджер зависимостей. Не переводим и не форкаем сам Codex CLI. Не включаем бинарники Codex, установщики ОС, Node.js или веса моделей в обычный учебный ZIP.

OpenSpec нужен разработчику, а не ученику. Публикацию самого курса как плагина и EPUB не включаем в первую поставку. Тема устройства плагинов в учебнике остаётся.

## Decisions

### 1. Переиспользование вместо нового приложения

Основной актив разработки — готовая Markdown→HTML сборка с обработкой ссылок, шаблоны, локальные ресурсы и тестовые заготовки. Перенос этих частей в новый проект не убирает необходимость переписать Claude-содержание, но создаёт дополнительную работу по интеграции.

Создаём собственный форк/копию репозитория под рабочим названием `codex-cli-course-ru`. Сохраняем исходную историю при наличии Git-репозитория; при старте только из ZIP фиксируем его SHA-256 и происхождение. Старое направление не поддерживаем параллельно. Не удаляем старый архив у пользователя.

### 2. Минимальная структура исходников

```text
AGENTS.md                    # инструкции разработчика; не принудительный наставник
README.md
course.json                  # порядок, ID, revision, зависимости и файлы уроков
sources.json                 # версия Codex, источники и связи с уроками
01-start/ ... 10-capstone/    # русский Markdown и quiz.json каждого модуля
reference/                   # собственный локальный справочник и происхождение
examples/<exercise-id>/      # starter, solution, broken и условия проверки
.agents/skills/learn/SKILL.md # единственный учебный навык
scripts/build_website.py     # существующий сборщик, адаптированный
scripts/verify.py            # общая проверка + режим проверки одного упражнения
scripts/check_updates.py     # сравнение релизов/источников по запросу
scripts/website_templates/   # сохранённые шаблоны, CSS, JS, locales/ui.ru.json (с поддержкой ui.en.json)
scripts/tests/               # существующие и новые тесты
maintenance/baseline/        # небольшие сохранённые сведения для сравнения
.learning/                  # локальные результаты; вне Git и учебного ZIP
openspec/                    # спецификации разработки; не зависимость ученика
```

Это не требование создать пустой файл на каждое имя заранее. Код и тесты появляются по мере завершения соответствующих задач. `course.json` заменяет одновременно старый `roadmap.json`, список CHAPTER_ORDER как независимый источник и отдельный каталог модулей в трекере. Словари локализации интерфейса организуются в расширяемом формате `locales/ui.<lang>.json` (основной и активный в v1 — `ru`, с возможностью добавления `en` без изменения архитектуры генератора).

Все исполняемые и учебные действия строго изолированы внутри рабочего каталога репозитория: глобальные пользовательские настройки (`~/.codex/`, `~/.agents/`, конфиги Codex Desktop и сторонние CLI-алиасы/провайдеры, такие как Codex-MiniMax) остаются неприкосновенными.

### 3. Десять модулей, а не десять механически переименованных папок

| ID модуля | Тема | Минимальный наблюдаемый результат |
|---|---|---|
| start | Подготовка и первый запуск | Различить режимы курса, проверить подготовленную среду и прочитать локальную справку. |
| workflow | Повседневная работа | Сформулировать ограниченную задачу, разобрать план, diff и результат тестов. |
| safety | Разрешения и безопасные изменения | Определить область записи и выполнить восстановление в учебном Git-репозитории. |
| instructions | Инструкции и контекст | Создать AGENTS.md; отличить инструкции, данные, память и политики команд. |
| sessions | Сессии и восстановление | Различить продолжение/ветвление разговора и возврат состояния файлов. |
| skills | Повторяемые действия и skills | Подготовить маленький навык; не путать его со встроенной slash-командой. |
| mcp | Внешние инструменты без внешней сети | Разобрать и испытать локальный read-only stdio-пример; Docs MCP — дополнительный сетевой пример. |
| automation | Неинтерактивная работа | Различить поток событий JSONL и итоговый результат, проверить обработку ошибки. |
| extensions | Hooks, субагенты и плагины | Разобрать минимальные локальные примеры, области действия и доверие; включать только подтверждённые для целевой версии варианты. |
| capstone | Итоговая практика | Исправить ограниченную ошибку, выполнить проверки и сохранить раздельные результаты. |

Уроки имеют смысловые ID, например `workflow.small-fix`, независимо от номера папки. В каждом модуле не менее трёх вопросов; материалы и тесты должны действительно проверять заявленную цель. Итоговая практика не требует деплоя, удалённого Git, доступа к GitHub или внешнего API.

Для функций, которые без модели нельзя воспроизвести, самостоятельный вариант — разбор включённой записи и проверка локального результата/конфигурации. Это полноценный доступ к теме, но не подтверждение живого владения Codex. Ученик видит эту границу в прогрессе.

### 4. Готовая поставка для file://

ZIP имеет корневой `index.html`, HTML уроков, локальные assets, материалы, `examples/`, справочник, навык, локальный проверяющий код и манифест. Ученик не запускает сборщик.

Все необходимые файлы, включая `.py`, `.sh`, `.toml`, `SKILL.md`, копируются в поставку либо имеют локальное читаемое представление с доступом к оригиналу. Текущую подмену таких ссылок на GitHub отключаем для учебных материалов. Относительные ссылки проверяются на реально упакованном дереве, включая глубокие страницы, кириллицу и пробелы.

Данные викторин и каталога встраиваются в HTML или обычный локальный JS при сборке: не использовать fetch локального JSON, ES-module imports и service worker как обязательные механизмы file://. Встраиваемый JSON безопасно экранируется, включая `</script>`. Страницы остаются читаемыми без JS.

Прогресс и викторины находятся на канонической `index.html`; страницы уроков — статические и возвращают к карте якорем с lesson_id. Не пытаемся синхронизировать localStorage разных file:// страниц. Экспорт/импорт обеспечивает перенос между браузерами, каталогами и терминалом. При недоступном хранилище сохраняем состояние в памяти и явно предлагаем экспорт до закрытия страницы.

Сохраняем существующий подход к локальным ресурсам. Для первой версии используем системный стек шрифтов с кириллицей. Не вводим загрузку шрифтов. Оставшиеся сторонние JS/CSS фиксируем точной версией, хешем и уведомлением об авторстве; не используем плавающую major-версию. Сборочные зависимости подготавливает сопровождающий, не ученик.

### 5. Один навык, без собственного агента поверх Codex

`$learn` читает `course.json`, выбранный Markdown и локальные ответы/подсказки. Не требует AskUserQuestion, MCP, специального UI или собственной базы знаний. В корневом AGENTS.md есть правила работы разработчика; учебный сценарий включается по запросу.

Оценивание викторины и проверка файлов не поручаются свободному тексту модели. Банк вопросов содержит ID и правильные ID; одинаковые фикстуры проверяют JS-оценивание и локальный расчёт. Проверка практики вызывается через режим `scripts/verify.py --exercise ...` и записывает машиночитаемый результат. Не добавляем отдельный сервис оценивания.

MCP-урок использует небольшой поставляемый stdio-сервер с одной безопасной операцией и локальными данными. Это учебная фикстура, а не общий сервер для всего курса. Базовая реализация без скачиваемых Python-пакетов; совместимость проверяется настоящим Codex. Если минимальный пример требует дополнительных зависимостей, их добавление сначала рассматривается как изменение этого решения, а не незаметный pip install у ученика.

Конфигурации hooks, агентов и плагинов лежат в примерах, не устанавливаются глобально и не подключаются все сразу. Форматы проверяются по текущему первичному источнику и реальным запуском. TOML/JSON-парсер доказывает только синтаксис, не семантику Codex.

### 6. Данные прогресса без лишней инфраструктуры

Базовая форма; точные проверки полей реализуются обычными функциями, без генератора моделей:

```json
{
  "schema_version": 1,
  "course_id": "codex-cli-course-ru",
  "course_version": "0.1.0",
  "lessons": {
    "workflow.small-fix": {
      "revision": 1,
      "read": false,
      "quiz": null,
      "exercise": null,
      "codex_run": null,
      "needs_review": false
    }
  },
  "unmapped": {}
}
```

`quiz` содержит question/option ID, число правильных, общее число, порог и время. `exercise` содержит exercise_id, revision, результат, способ проверки и хеш проверенных входов. `codex_run` дополнительно содержит версию CLI, модель/провайдер, время и ссылку на локальное доказательство; отсутствие данных не превращается в успешный статус.

Для импорта: сначала полностью проверить документ в памяти, затем применить его атомарно; не исполнять строки и не сливать произвольные ключи в JS-объекты. Максимум 1 МиБ. Автоматического объединения конфликтующих экспортов нет: показать сводку и запросить подтверждение замены. Перед заменой или сбросом разрешить экспорт текущего состояния. Неизвестные ID того же курса сохраняются в `unmapped`; другой course_id отклоняется. Изменённая revision сохраняет историю, но снимает актуальность подтверждения.

Это локальный учебный журнал, не криптографически защищённый экзаменационный сертификат. Поля происхождения не защищают от пользователя, намеренно подделавшего собственный файл.

### 7. Обновления без сервиса и автоисправлений

Один `sources.json` содержит `target_cli`, `tested_cli`, профиль испытаний и список `{id, url, section, checked_at, fingerprint, lesson_ids}`. На старте целевой кандидат — 0.160.0; `tested_cli` остаётся null до реального прогона. Не поддерживаем одновременно много версий CLI.

В `maintenance/baseline/` храним небольшой manifest и локальную справку реально используемых команд. Полный зеркальный архив всех OpenAI-сайтов не нужен. Содержательная офлайн-база курса — собственный русский справочник, а не обязательное чтение удалённой страницы. Временные загрузки источников для сравнения не попадают в учебный ZIP.

Предлагаемый контракт одного скрипта:

```bash
# Автономное сравнение двух заранее подготовленных наборов.
python scripts/check_updates.py --baseline maintenance/baseline --candidate maintenance/candidate --report .learning/update-report.json

# Только по явному запросу: получить публичные сведения в candidate.
python scripts/check_updates.py --fetch --candidate maintenance/candidate --report .learning/update-report.json
```

В сетевом режиме разрешены только зарегистрированные официальные источники; сохраняются исходный и конечный адрес редиректа. Не выполнять команды из текста релиза, не скачивать/устанавливать Codex и не менять рабочие уроки. CLI-справку новой версии сопровождающий снимает с отдельно подготовленного бинарника. Отсутствующие сведения делают отчёт incomplete, а не «совместимо».

Рабочий цикл: кандидат → отчёт изменений → ручное решение по каждому затронутому уроку → правка revision и примеров → весь регрессионный прогон → явный выпуск → сохранение прежнего ZIP. Изменение документации не всегда является изменением поведения. Локальные фикстуры сравнения позволяют тестировать этот процесс без выхода нового реального релиза.

### 8. Проверки добавляются вместе с функциональностью

Используем имеющийся pytest. Для проверки браузера добавляем только dev-зависимость Playwright с заранее установленными Chromium и Firefox. Рантайм ученика этих инструментов не содержит. Точные версии зависимостей и браузеров фиксируются перед первым прогоном; новая широкая матрица ОС не нужна.

`verify.py --profile offline` запускает структуру, локальные ссылки, содержимое, данные, упражнения, фикстуры обновления и file://-сценарии. `--profile live` — настоящий CLI и доступную модель. `--profile release` объединяет актуальные доказательства обоих профилей и ручной проверки для одного кандидата. Отсутствие среды — BLOCKED с ненулевым кодом, а не пропуск.

Автоматические примеры имеют тип: `local-runnable`, `codex-runnable`, `transcript`, `illustrative` или `dangerous-demonstration`. Первые два исполняются соответственно в offline/live профилях; остальные не исполняются и проверяются редакционно. Все опубликованные runnable-примеры входят в приёмку параметризованными тестами, а не только примеры из пилота.

Конкретные отчёты, рубрики, команды и правила выпуска: [validation.md](validation.md). `traceability.json` — небольшой список проверок, не новая тестовая платформа.

## Risks / Trade-offs

- **file:// ограничивает хранилище и API браузера.** Одна каноническая страница прогресса, отсутствие обязательного fetch, ручной экспорт и испытания в двух браузерах.
- **Полный офлайн не создаёт вычислительную модель.** Материалы и самостоятельная практика доступны; живой локальный Codex требует заранее подготовленного провайдера и подходящего оборудования. Конкретная локальная модель не заявляется сертифицированной в v1 без отдельного прогона.
- **Ответы модели недетерминированы.** Рубрика, проверка файлов/действий, несколько новых сессий. Успех конечного набора тестов не доказывает безошибочность всех будущих ответов.
- **Документация может опережать выбранный CLI.** Локальная CLI-справка, проверка используемых функций на точном бинарнике и явные статусы.
- **Старые тесты утверждают старую семантику.** Сохранять полезные проверки, но адаптировать ожидания по спецификации; не удалять сбой без объяснения.
- **Ручная редактура не заменяется поиском латиницы.** Автоматический аудит явных регрессий дополняется просмотром русского текста, учебных целей и официальных источников.

## Migration Plan

Сохранить baseline → зафиксировать версию и запустить старые применимые тесты → реализовать вертикальный пилот → пройти его offline/live проверки → переносить по модулю → удалить недействующий Claude-контент из публикации → испытать обновление на фикстуре → выполнить полную приёмку.

До приёмки всех обязательных модулей пилот не называется полным релизом. Прежний архив и лицензия сохраняются; записи OpenSpec не архивируются как выполненные до завершения tasks. Откат — возврат исходников/поставки, а не сброс личных результатов.
