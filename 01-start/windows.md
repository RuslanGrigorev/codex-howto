# Windows, WSL и пути к учебным файлам

## Чему вы научитесь

Научитесь правильно выбирать между нативной средой Windows (PowerShell / cmd) и подсистемой WSL2 (Ubuntu / Debian), понимать различия в формате путей (`C:\...` vs `/mnt/c/...`), диагностировать особенности прав доступа и символических ссылок в Windows, а также предотвращать ошибки кросс-платформенной кодировки и окончаний строк.

## Что нужно перед началом

1. Компьютер под управлением Windows 10/11 (или Linux/macOS для сравнительного анализа).
2. Установленный PowerShell 7+ или дистрибутив WSL2.
3. Понимание различий между файловыми системами NTFS и ext4.

## Схема процесса

Сравнение двух альтернативных маршрутов выполнения в Windows:

```text
Вариант 1: Нативная Windows (PowerShell)
┌─────────────────────────────────────────────────────────────┐
│ Терминал: PowerShell 7+                                     │
│ Пути: C:\Users\User\projects\codex-howto                    │
│ Символические ссылки: требуют SeCreateSymbolicLinkPrivilege │
│ Окончания строк: CRLF (рекомендуется настроить Git на LF)   │
└─────────────────────────────────────────────────────────────┘

Вариант 2: WSL2 (Linux внутри Windows)
┌─────────────────────────────────────────────────────────────┐
│ Терминал: bash / zsh внутри WSL2                            │
│ Пути: /home/user/projects/codex-howto (быстро на ext4)      │
│ или /mnt/c/Users/... (медленный доступ через 9P/drvfs)      │
│ Символические ссылки: полноценные Linux symlinks без прав   │
│ Изоляция песочницы: нативный bubblewrap / namespaces        │
└─────────────────────────────────────────────────────────────┘
```

Главное правило: выберите **один** маршрут и не переключайтесь между ними во время выполнения одного упражнения.

## Команды и параметры

Диагностические команды для нативной Windows (PowerShell):

```powershell
# Проверка версии и путей к исполняемым файлам в PowerShell
Get-Command python | Select-Object -ExpandProperty Source
Get-Command git | Select-Object -ExpandProperty Source
Get-Command codex | Select-Object -ExpandProperty Source

# Проверка рабочей директории в Python
python -c "from pathlib import Path; print(Path.cwd())"

# Проверка статуса прав на символические ссылки
python -c "import os; print('Symlink support:', hasattr(os, 'symlink'))"
```

Диагностические команды для WSL2 (Bash):

```bash
# Проверка путей в Linux WSL
which python3
which git
which codex
pwd
```

## Разбор примера

Рассмотрим типичную ошибку смешения сред:
1. Репозиторий склонирован в `C:\Users\Mi\Desktop\projects\codex-howto`.
2. Ученик запускает WSL и пытается запустить тесты:
   ```bash
   cd /mnt/c/Users/Mi/Desktop/projects/codex-howto
   python3 scripts/verify.py --exercise small-fix --workspace .learning/workspaces/small-fix
   ```
3. Файловая система `/mnt/c` монтируется через драйвер `drvfs`. В ней не поддерживаются нативные POSIX-права доступа к файлам и создание символических ссылок без административных привилегий Windows.
4. В результате тесты, требующие прав на симлинки, падают с `WinError 1314` или ошибками доступа.
5. Правильное решение: либо выполнять всё в нативном PowerShell с включённым режимом разработчика Windows (Developer Mode), либо клонировать проект строго внутрь файловой системы WSL: `~/projects/codex-howto`.

## Ограничения и безопасность

1. **Привилегия `SeCreateSymbolicLinkPrivilege`**: в нативной Windows создание символических ссылок по умолчанию запрещено для обычных пользователей. Для включения активируйте «Режим разработчика» (Developer Mode) в параметрах Windows.
2. **Пробелы в путях**: пути вида `C:\Users\Иван Иванов\Desktop\...` часто ломают сторонние CLI-инструменты при отсутствии кавычек. Всегда размещайте учебные репозитории в путях без пробелов (например, `C:\dev\codex-howto`).
3. **Кодировка UTF-8**: PowerShell 5.1 по умолчанию использует ANSI/OEM кодировки. В скриптах проверки курса принудительно используется переменная `PYTHONUTF8=1` и `PYTHONIOENCODING=utf-8`.

## Ошибки и диагностика

| Ошибка | Причина | Способ диагностики и исправления |
|---|---|---|
| `WinError 1314: Клиент не обладает требуемыми правами` | Попытка создания симлинка в Windows без прав Developer Mode. | Включите Developer Mode в настройках Windows («Для разработчиков») или используйте WSL2 на ext4. |
| `UnicodeDecodeError: 'cp1251' codec can't decode byte...` | Несовместимость кодировки консоли Windows. | Запускайте команды с флагом: `python -X utf8 ...` или установите `$env:PYTHONUTF8="1"`. |
| Путь вида `/mnt/c/...` не распознаётся в PowerShell | Использование синтаксиса путей Linux внутри Windows. | В PowerShell используйте стандартные пути Windows `C:\...` или относительные пути. |

## Практика

1. Откройте PowerShell и проверьте, как Python видит текущую директорию:
   ```powershell
   python -c "from pathlib import Path; print('Текущий диск и путь:', Path.cwd())"
   ```
2. Проверьте кодировку консоли и правильность отображения кириллицы:
   ```powershell
   python -c "print('Проверка UTF-8: Привет, Codex CLI!')"
   ```
3. Подготовьте и проверьте упражнение `small-fix` в текущей среде:
   ```powershell
   python scripts/verify.py --prepare small-fix
   python scripts/verify.py --exercise small-fix --workspace .learning/workspaces/small-fix
   ```

## Самопроверка

Критерии завершения:
1. Вы выбрали одну постоянную среду (PowerShell или WSL2).
2. Вы понимаете причину возникновения ошибки `WinError 1314` при создании симлинков в Windows.
3. Проверочный запуск упражнения `small-fix` завершается со статусом `PASS`.

<details>
<summary>Контрольные вопросы для самопроверки</summary>

- **Вопрос**: Почему не рекомендуется размещать учебные репозитории в каталогах с пробелами в пути?
- **Ответ**: Пробелы требуют обязательного экранирования кавычками во всех аргументах CLI и вызовах инструментов, что часто приводит к случайным ошибкам парсинга путей.
- **Вопрос**: Как принудительно заставить Python использовать UTF-8 в Windows?
- **Ответ**: Передать флаг `-X utf8` при вызове интерпретатора или установить переменную среды `PYTHONUTF8=1`.

</details>
