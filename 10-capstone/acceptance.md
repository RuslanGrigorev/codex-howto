# Приёмка учебного проекта: доказательства вместо обещаний

## Чему вы научитесь

- Формировать проверяемые инженерные отчеты о приемке проекта на основе доказательств (Evidence-Based Acceptance).
- Отличать локальный самоотчет ученика от криптографически верифицируемого релизного пакета.
- Понимать семантику статусов качества: `PASS`, `BLOCKED`, `NOT_RUN`, `SKIP` — и не подменять невыполненные тесты фиктивным успехом.
- Валидировать целостность дерева файлов с помощью хэш-сумм SHA-256 и отчетов `validation.json`.

## Что нужно перед началом

- Завершенное выполнение упражнений курса и наличие сгенерированных логов сессий.
- Понимание структуры файла валидации `reference/validation.md`.
- Установленный Python 3.10+ и Codex CLI 0.160.0.

## Схема процесса

Конвейер верификации доказательств при приемке:

```
┌────────────────────────────────────────────────────────┐
│             Исходный артефакт / Кодовая база           │
├────────────────────────────────────────────────────────┤
│ Хэш коммита Git / SHA-256 дерева файлов                │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│             Независимые проверочные раннеры            │
├────────────────────────────────────────────────────────┤
│ 1. scripts/check_project.py catalog ──> Каталог курса  │
│ 2. pytest -q scripts/tests          ──> Регрессии кода │
│ 3. scripts/verify.py --profile offline ─> Офлайн-маршрут│
│ 4. scripts/check_site.py             ──> Целостность web│
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│         Формирование матрицы Evidence Matrix           │
├────────────────────────────────────────────────────────┤
│ [PASS]    ──> Подтверждено реальным запуском раннера   │
│ [BLOCKED] ──> Невозможно выполнить (нет прав/окружения)│
│ [NOT_RUN] ──> Тест не запускался (отсутствует модель)  │
│ ПРАВИЛО: BLOCKED, SKIP и NOT_RUN НЕ являются успехом!  │
└────────────────────────────────────────────────────────┘
```

## Команды и параметры

Команды комплексной проверки готовности проекта:

```bash
# Валидация структуры каталога курса
python scripts/check_project.py catalog

# Регрессионное тестирование скриптов
python -m pytest -q scripts/tests

# Полная автономная проверка маршрута без сетевых вызовов
python scripts/verify.py --profile offline

# Проверка ссылок и разметки собранного статического сайта
python scripts/check_site.py --site .learning/site
```

Формат структуры отчета в `acceptance_report.md`:

```text
Артефакт: codex-course-candidate.zip
SHA-256 дерева: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
Версия CLI: 0.160.0 (baseline)
Статус офлайн-проверок: PASS (4/4 проверок)
Статус live-моделей: NOT_RUN (тесты с реальным API не запускались)
Ограничения: Автономный режим без сетевых интеграций
```

## Разбор примера

Рассмотрим процесс защиты результатов проекта перед заказчиком или техлидом:

1. Разработчик запускает офлайн-проверку:
   ```bash
   python scripts/verify.py --profile offline
   ```
2. Система выполняет тесты упражнений, проверку схем данных и целостности ссылок.
3. В отчете разработчик честно фиксирует:
   - Все 9 автономных упражнений: `PASS`.
   - Проверка реального запуска Codex: `NOT_RUN` (модели не запускались, использовался документальный baseline 0.160.0).
4. Техлид видит прозрачную матрицу доказательств: отсутствуют попытки выдать непроверенные фичи за работающие.
5. Проект успешно принимается с точным перечнем ограничений.

## Ограничения и безопасность

- Статусы `BLOCKED`, `SKIP` и `NOT_RUN` категорически **запрещено** интерпретировать как успешное прохождение (PASS).
- Нельзя утверждать о нативной совместимости CLI без предоставления точной версии бинарника, имени модели и лога сессии.
- Локальный файл прогресса ученика не является криптографическим сертификатом: он предназначен исключительно для личного трекинга.

## Типовые ошибки

1. **Фальсификация матрицы доказательств**: замена статуса `NOT_RUN` на `PASS` ради красивого отчета.
2. **Игнорирование хэша дерева**: отправка отчета, сформированного для одной ветки, вместе с архивом другой ветки.
3. **Принятие unit-тестов за e2e**: утверждение, что сайт работает во всех браузерах, если проверен только синтаксис HTML.

## Практика

1. Соберите итоговую матрицу проверок вашего проекта по трем направлениям: каталог, тесты, офлайн-маршрут.
2. Зафиксируйте хэш коммита Git и проверьте соответствие статусов реальному выводу терминала.
3. Составьте документ приемки с явным разделением на подтвержденные результаты и невыполненные проверки.

## Самопроверка

<details>
<summary>Подсказка и критерии самопроверки</summary>

- Убедитесь, что каждый статус `PASS` в вашем отчете подкреплен сохраненным логом выполнения проверочной команды.
- Проверьте, что проверки, требовавшие реального запуска модели, честно помечены как `NOT_RUN`.
- Критерий успешности: отчет содержит полную и достоверную картину состояния проекта без умалчивания ограничений.

</details>
