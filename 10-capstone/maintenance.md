# Как проверять курс после нового релиза Codex

## Чему вы научитесь

- Регламентировать процесс обновления курса при выходе новых версий Codex CLI.
- Использовать инструменты аудита покрытия `check_coverage.py` и анализа обновлений `check_updates.py`.
- Разделять изменения документации, изменения синтаксиса флагов и глубокие изменения ядра.
- Проводить повторную верификацию без слепого повышения версии совместимости.

## Что нужно перед началом

- Актуальный локальный репозиторий курса.
- Файл источников `sources.json` и инвентарь `reference/coverage.md`.
- Установленный Codex CLI 0.160.0 (baseline) или более свежий релиз для тестирования.

## Схема процесса

Алгоритм ревизии и обновления материалов курса при выходе новой версии CLI:

```
[Выход нового релиза Codex CLI, напр. v0.165.0]
                        │
                        ▼
┌────────────────────────────────────────────────────────┐
│             Фаза 1: Сбор диффа и инвентаризация        │
├────────────────────────────────────────────────────────┤
│ 1. Сравнение cli-help и slash-команд                   │
│ 2. python scripts/check_updates.py                     │
│ 3. Выявление новых флагов и удаленных параметров       │
└───────────────────────┬────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────────┐
│             Фаза 2: Точечная актуализация уроков       │
├────────────────────────────────────────────────────────┤
│ - Обновление справочника reference/coverage.md         │
│ - Пометка удаленных команд как "historical_removed"    │
│ - Добавление новых возможностей в соответствующие темы │
└───────────────────────┬────────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────────┐
│             Фаза 3: Повторная верификация              │
├────────────────────────────────────────────────────────┤
│ 1. python scripts/check_project.py catalog ──> PASS    │
│ 2. python scripts/verify.py --profile offline ──> PASS │
│ 3. Формирование нового протокола tested_cli            │
└────────────────────────────────────────────────────────┘
```

## Команды и параметры

Команды аудита обновлений и проверки покрытия:

```bash
# Проверка покрытия инвентаря команд и флагов материалами курса
python scripts/check_coverage.py

# Сверка с новыми снимками источников (без сетевых запросов)
python scripts/check_updates.py

# Проверка контента на соответствие контрактам курса
python scripts/check_content_contract.py --stage ALL
```

Пример фиксации изменения в `reference/coverage.md`:

```markdown
| Команда / Параметр | Источник | Статус покрытия | Примечание |
| :--- | :--- | :--- | :--- |
| `codex mcp-server` | CLI 0.150 | historical_removed | Заменена на `codex mcp run` в 0.160.0 |
| `/goal` | CLI 0.160.0 | covered | Подробно разобрана в 02-workflow/plan-goal.md |
```

## Разбор примера

Рассмотрим реакцию на появление нового флага `--auto-compact` в CLI:

1. Запускаем `check_updates.py`: скрипт сигнализирует о появлении нового флага в официальной документации.
2. Определяем затронутые материалы:
   - Урок [Память, сжатие контекста и сводки](../04-instructions/memory.md).
   - Справочник [Интерфейс и команды](../reference/commands.md).
   - Тест на знание флагов управления памятью.
3. Вносим описание флага в урок, объясняя его границы и значение по умолчанию.
4. Проверяем, что офлайн-маршрут сохраняет стабильность:
   ```bash
   python scripts/verify.py --profile offline
   ```
5. Только после получения лога реального запуска на новой версии повышаем значение `tested_cli`.

## Ограничения и безопасность

- Никогда не повышайте версию `tested_cli` автоматически лишь на основании того, что документация была обновлена: статус реальной совместимости требует фактического запуска на целевой платформе.
- Удаленные из продукта команды помечайте как исторические (`historical_removed`), а не удаляйте бесследно: это помогает пользователям, использующим разные версии.
- Не включайте автоматический скрейпинг сайтов без согласования: курс должен оставаться полностью автономным.

## Типовые ошибки

1. **Слепое повышение номера версии**: замена 0.160.0 на 0.170.0 во всех заголовках без тестирования бинарника.
2. **Удаление устаревших команд**: молчаливое стирание информации о старых флагах, приводящее в замешательство пользователей на LTS-версиях.
3. **Игнорирование тестов**: обновление текста уроков без запуска проверочных скриптов проекта.

## Практика

1. Запустите скрипт проверки покрытия `python scripts/check_coverage.py` и изучите его отчет.
2. Смоделируйте появление нового параметра конфигурации в `config.toml` и определите уроки, требующие обновления.
3. Проверьте актуальность файла `sources.json` и целостность ссылок курса.

## Самопроверка

<details>
<summary>Подсказка и критерии самопроверки</summary>

- Убедитесь, что `check_coverage.py` подтверждает 100% покрытие всех закрепленных элементов инвентаря.
- Проверьте, что ни одна удаленная команда не представлена как активная рабочая функция.
- Критерий успешности: процесс ревизии документирован, воспроизводим и не нарушает автономность курса.

## Источники и доступность

Практика требует установленного Codex и доступной выбранной модели. Без модели выполните разбор примера и подготовьте ожидаемый результат; реальный запуск остаётся невыполненным. Целевая версия — 0.160.0. Документальная сверка: 2026-10-05; она не заменяет протокол запуска на вашей ОС.
