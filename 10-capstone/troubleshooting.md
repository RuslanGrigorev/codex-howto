# Диагностика, обновление и границы покрытия

## Чему вы научитесь

- Диагностировать комплексные многоуровневые сбои в окружении разработки Codex CLI: операционная система, сеть, клиент, модель, расширения и скрипты проекта.
- Проверять конфигурацию и собирать обезличенные дампы диагностики без риска утечки учетных данных и секретов.
- Работать с матрицей покрытия публичного инвентаря команд (`reference/coverage.md`).
- Подготавливать качественные баг-репорты с воспроизводимыми шагами и логами.

## Что нужно перед началом

- Завершение всех предшествующих уроков практикума.
- Доступ к справочным материалам курса и матрице валидации.
- Установленный Codex CLI 0.160.0.

## Схема процесса

Многоуровневый алгоритм локализации дефектов:

```
[Возникла ошибка при работе с Codex CLI]
                     │
                     ▼
┌────────────────────────────────────────────────────────┐
│  Слой 1: Окружение и процесс ОС                        │
│  - Установлен ли бинарник? Доступен ли в PATH?         │
│  - Достаточно ли прав и дискового пространства?        │
└────────────────────┬───────────────────────────────────┘
                     │ В норме
                     ▼
┌────────────────────────────────────────────────────────┐
│  Слой 2: Авторизация и сетевые соединения              │
│  - Валиден ли токен провайдера? (без утечки в логи!)   │
│  - Нет ли блокировок файрвола / корпоративного прокси? │
└────────────────────┬───────────────────────────────────┘
                     │ В норме
                     ▼
┌────────────────────────────────────────────────────────┐
│  Слой 3: Конфигурация и песочница                      │
│  - Валиден ли синтаксис config.toml?                   │
│  - Не блокирует ли sandbox целевой путь записи?        │
└────────────────────┬───────────────────────────────────┘
                     │ В норме
                     ▼
┌────────────────────────────────────────────────────────┐
│  Слой 4: Поведение модели и расширения (MCP/Hooks)     │
│  - Не исчерпан ли лимит токенов контекста?             │
│  - Не завершился ли MCP-сервер аварийно?               │
└────────────────────────────────────────────────────────┘
```

## Команды и параметры

Команды сбора отладочной информации и проверки конфигурации:

```bash
# Проверка версии установленного клиента
codex --version

# Проверка базовой справки и доступных команд
codex --help

# Проверка матрицы покрытия инвентаря команд
python scripts/check_coverage.py

# Сверка с обновлениями официальных источников
python scripts/check_updates.py
```

Интерактивные слеш-команды диагностики в сессии TUI:
- `/status` — сводка по модели, песочнице и расходу токенов.
- `/permissions` — перечень активных прав и ограничений песочницы.
- `/skills` — список зарегистрированных навыков.
- `/mcp` — инспекция подключенных серверов Model Context Protocol.

## Разбор примера

Рассмотрим диагностику загадочного сбоя: «Агент утверждает, что исправил ошибку, но код остался неизменным»:

1. Проверяем Слой 1 (ОС): диск не переполнен, права на файл есть.
2. Проверяем Слой 2 (Сеть/Провайдер): ответ от модели получен успешно.
3. Проверяем Слой 3 (Песочница):
   - Смотрим вывод `/permissions` в сессии: оказывается, клиент был запущен с флагом `--sandbox read-only`!
   - Инструмент модификации файлов молча возвращал ошибку нарушения песочницы, которую модель скрыла за общими фразами.
4. Исправление: перезапускаем сессию с нужным уровнем прав:
   ```bash
   codex --sandbox workspace-write
   ```
5. Агент успешно вносит изменения в файл, что подтверждается командой `git diff`.

## Ограничения и безопасность

- При формировании отчетов об ошибках никогда не прикрепляйте файлы `auth.json`, дамп окружения `env` или скриншоты с приватными токенами.
- Не запускайте скрытые или недокументированные отладочные команды ядра, помеченные в исходном коде как внутренние для разработчиков CLI.
- Помните, что матрица покрытия фиксирует соответствие стандарту документации версии 0.160.0; поведение более старых или экспериментальных сборок может отличаться.

## Типовые ошибки

1. **Публикация секретов в отчетах**: отправка полного лога сессии в публичный issue-трекер без предварительной фильтрации токенов.
2. **Смешение слоев сбоя**: попытка исправить промпт модели, когда на самом деле процесс блокируется песочницей операционной системы.
3. **Объявление полной совместимости без проверки**: утверждение о 100% поддержке функционала без сверки с `reference/coverage.md`.

## Практика

1. Смоделируйте ошибку каждого слоя: неверный путь к файлу, синтаксическая ошибка в `config.toml`, запрет записи песочницей.
2. Сформируйте обезличенный отчет об ошибке с точной версией CLI, ОС, командой запуска и сообщением об ошибке.
3. Запустите скрипт проверки покрытия `python scripts/check_coverage.py` и подтвердите отсутствие белых пятен в инвентаре.
