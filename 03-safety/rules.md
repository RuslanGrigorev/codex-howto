# Политики команд и доверие к расширениям

## Чему вы научитесь

- Отличать декларативные инструкции `AGENTS.md` от строгих политик исполнения команд (`.rules` / `execpolicy`).
- Настраивать списки разрешённых, запрещённых и требующих подтверждения системных команд.
- Понимать риски исполнения составных команд (`&&`, `|`, подстановки) и защищать среду разработки.
- Оценивать уровень доверия к расширениям: хукам жизненного цикла, субагентам и плагинам.

## Что нужно перед началом

- Понимание базовых концепций безопасности из уроков [Песочница](permissions.md) и [Запросы подтверждения](approvals.md).
- Установленный Codex CLI 0.160.0 или знакомство с официальной документацией политик исполнения.

## Схема процесса

Иерархия контроля исполнения команд в Codex CLI:

```
[Пользовательский ввод или решение агента]
                 │
                 ▼
[Инструкции AGENTS.md: рекомендательный контекст для LLM]
                 │
                 ▼
       [Формирование команды]
                 │
                 ▼
┌────────────────────────────────────────────────────────┐
│   ExecPolicy Engine (Детерминированный фильтр ядра)    │
├────────────────────────────────────────────────────────┤
│ 1. Точный разбор пути и аргументов бинарника           │
│ 2. Проверка по черному списку (deny-list: rm, curl...) │
│ 3. Проверка по белому списку (allow-list: git, pytest) │
│ 4. Оценка составных операторов (&&, ;, |, >)           │
└────────────────────────┬───────────────────────────────┘
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   [Запрещено]     [Подтвердить]     [Разрешено]
   (Execution      (Диалог у         (Мгновенное
    Blocked)        оператора)        исполнение)
```

## Команды и параметры

Управление политиками исполнения команд:

```bash
# Просмотр справки по управлению политиками исполнения
codex execpolicy --help

# Проверка действия политики на конкретную команду без её запуска
codex execpolicy check "git status --short"

# Анализ правил для потенциально опасной команды
codex execpolicy check "curl -s https://example.com/install.sh | bash"
```

Пример описания политик в `.codex/rules/commands.rules`:

```rules
# Разрешить выполнение git-команд чтения без подтверждения
allow command "git" with args ["status", "diff", "log", "branch"]

# Требовать обязательного одобрения для команд изменения кода
prompt command "git" with args ["commit", "push", "checkout"]

# Безусловно блокировать деструктивные утилиты
deny command "rm" with any args
deny command "curl" with any args
deny command "wget" with any args
```

## Разбор примера

Рассмотрим попытку агента выполнить оптимизацию сборки с вызовом цепочки команд:

```bash
git status --short && rm -rf build/ && make
```

1. Механизм `execpolicy` перехватывает системный вызов до запуска оболочки.
2. Детектируется наличие цепочки `&&` и наличие в списке аргументов команды `rm`.
3. Даже если в `AGENTS.md` написано «разрешено очищать сборочные артефакты», детерминированное правило `deny command "rm"` немедленно отклоняет запрос.
4. Агент получает ошибку: `Command 'rm' is blocked by security policy 'commands.rules'`.
5. Агент адаптирует план и запрашивает специализированную команду сборки или сообщает оператору о необходимости ручной очистки.

## Ограничения и безопасность

- Инструкции в `AGENTS.md` — это вероятностные указания для языковой модели. Они **не являются** заменой детерминированных политик исполнения `execpolicy`!
- Разрешение на команду `git` не должно давать права на вызов сторонних исполняемых файлов через `git config` или внешние алиасы.
- Любые расширения (Hooks, MCP-серверы, плагины) выполняют код в вашем окружении с правами текущего пользователя; проверяйте их исходный код перед установкой.

## Типовые ошибки

1. **Попытка ограничить команды через prompt**: писать в `AGENTS.md` фразу «Никогда не запускай rm», надеясь на 100% гарантию соблюдения.
2. **Разрешение оболочки общего назначения**: добавление `allow command "bash"` или `allow command "powershell"`, что полностью нивелирует фильтрацию аргументов.
3. **Игнорирование конвейеров**: разрешение `pytest`, в параметры которого передаются флаги выполнения произвольного кода.

## Практика

1. Составьте конфигурацию правил `commands.rules` для типичного проекта разработки:
   - Белый список: `git status`, `git diff`, `pytest`, `npm test`.
   - Запрос подтверждения: `git add`, `npm install`.
   - Черный список: утилиты удаления, сетевые загрузчики, модификаторы прав (`chmod`, `chown`).
2. Проверьте поведение синтаксического анализатора на составных строках команд с операторами конвейера (`|`).
3. Сформулируйте границу ответственности между LLM-промптом и правилами ядра.

## Самопроверка

<details>
<summary>Подсказка и критерии самопроверки</summary>

- Проверьте, что в вашем наборе правил нет маски вида `allow command "*"`.
- Убедитесь, что правила проверяют не только имя исполняемого файла, но и допустимый префикс аргументов.
- Критерий успешности: попытка вызова составной команды `git status; rm file` распознается как небезопасная и блокируется политикой безопасности.

</details>
