# Проверка песочницы на безопасном примере

## Чему вы научитесь

- Безопасно тестировать ограничения файловой системы песочницы Codex CLI без риска для рабочих данных.
- Создавать изолированный тестовый маркер и проверять поведение агента в режиме `read-only`.
- Различать системный отказ песочницы и ошибки интерпретатора команд.
- Проверять сохранность файлов с помощью независимых терминальных команд после завершения сессии.

## Что нужно перед началом

- Отдельный временный каталог для учебного эксперимента (например, `.learning/workspaces/sandbox-lab`).
- Установленный Codex CLI или понимание документационной модели его работы.
- Отсутствие секретов, персональных данных и важных репозиториев в тестовом окружении.

## Схема процесса

Лабораторный цикл проверки песочницы:

```
[1. Подготовка маркера] ──> marker.txt: "INIT_VAL"
            │
            ▼
[2. Старт Codex в read-only] ──> codex --sandbox read-only
            │
            ▼
[3. Попытка записи через агента] ──> агент вызывает запись в marker.txt
            │
            ├───────────────┬────────────────┐
            ▼               ▼                ▼
     [Отказ ОС/SELinux] [Отказ CLI]   [Запись прошла]
            │               │                │
            ▼               ▼                ▼
       (Ожидаемо)      (Ожидаемо)    (Нарушение песочницы!)
            │               │                │
            └───────┬───────┘                │
                    ▼                        ▼
     [4. Независимая проверка]        [Аудит прав ОС /
      cat marker.txt == "INIT_VAL"     ошибки профиля]
```

## Команды и параметры

Команды управления и тестирования песочницы:

```bash
# Просмотр параметров встроенной песочницы
codex sandbox --help

# Запуск изолированной сессии с полным запретом записи и отключенными подсказками
codex --sandbox read-only --ask-for-approval never

# Проверка ограничений на конкретную директорию
codex --sandbox workspace-write --sandbox-path ./safe-dir
```

Конфигурационный профиль в `.codex/config.toml`:

```toml
[sandbox]
mode = "read-only"
writable_paths = []
deny_network = true
```

## Разбор примера

1. Создаём маркерный файл перед запуском:
   ```bash
   mkdir -p /tmp/sandbox-test && cd /tmp/sandbox-test
   echo "ORIGINAL_CONTENT_SAFE" > marker.txt
   ```
2. Запускаем сессию в режиме только для чтения:
   ```bash
   codex --sandbox read-only --ask-for-approval never
   ```
3. Формулируем запрос к агенту:
   «Попробуй перезаписать файл marker.txt строкой OVERWRITTEN».
4. Наблюдаем реакцию инструмента: инструмент записи (apply_patch или bash) возвращает ошибку `Operation not permitted (os error 1)` или `Sandbox read-only violation`.
5. Завершаем сессию и проверяем маркер в системной консоли:
   ```bash
   cat marker.txt
   # Вывод: ORIGINAL_CONTENT_SAFE
   ```

## Ограничения и безопасность

- Никогда не используйте системные каталоги (`/etc`, `/usr`, `C:\Windows`) или пользовательский корень (`~`) для проверки песочницы.
- Помните, что независимый тест в Python (например, `pytest`) проверяет лишь логику скриптов, но не гарантирует аппаратную или ядерную изоляцию песочницы на вашей конкретной ОС.
- На Windows изоляция процесса может отличаться от Linux bubblewrap/landlock; всегда сверяйте платформенные ограничения.

## Типовые ошибки

1. **Тестирование на реальном коде**: запуск проверки перезаписи в рабочем Git-репозитории.
2. **Ложноположительный вывод**: считать ошибку синтаксиса Bash («command not found») доказательством работы песочницы.
3. **Доверие ответу модели**: верить утверждению «Я не смог изменить файл», не выполнив независимую проверку `cat marker.txt`.

## Практика

1. Подготовьте учебную директорию с файлом `marker.txt`, содержащим хэш-сумму или контрольную фразу.
2. Запустите сессию Codex CLI в режиме `read-only`.
3. Попросите агента прочитать файл (должно завершиться успехом), а затем добавить в конец строку `tampered` (должно быть заблокировано).
4. Зафиксируйте в отчёте:
   - Содержимое файла до сессии.
   - Точный текст ошибки песочницы, полученной агентом.
   - Содержимое файла после завершения сессии.

## Самопроверка

<details>
<summary>Подсказка и критерии самопроверки</summary>

- Убедитесь, что `marker.txt` остался идентичен исходному байт-в-байт (`diff marker.txt.orig marker.txt` возвращает 0 различий).
- Проверьте код ошибки: признаком работы песочницы является отказ доступа операционной системы (PermissionDenied / EPERM), а не ошибка парсинга параметров.
- Если файл изменился — песочница не активна в текущем окружении. Зафиксируйте инцидент и переключитесь на более строгий профиль изоляции.

</details>
