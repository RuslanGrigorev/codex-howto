## 1. Режимы песочницы (Sandbox) в Codex CLI

По умолчанию Codex CLI заботится о защите системы от случайных или деструктивных правок. С помощью флага `-s, --sandbox` вы явно определяете уровень доступа:

| Режим песочницы | Чтение файлов | Запись в workspace | Запись вне workspace | Когда использовать |
|---|---|---|---|---|
| `read-only` | Любые файлы проекта | Запрещена | Запрещена | Аудит кода, исследовательские запросы, код-ревью |
| `workspace-write` | Любые файлы проекта | Разрешена | **Запрещена** | Стандартная повседневная разработка (рекомендуется) |
| `danger-full-access` | Все файлы ОС | Разрешена | Разрешена | Только в изолированных Docker-контейнерах |

### Пример запуска только на чтение:
```bash
codex -s read-only "Проанализируй архитектуру и найди потенциальные уязвимости в auth.py"
```

Если модель попытается модифицировать файлы в этом режиме, рантайм вернет ошибку прав доступа, и диск останется в исходном состоянии.

## 2. Политика подтверждения опасных действий (--ask-for-approval)

Флаг `-a, --ask-for-approval` регулирует интерактивность сессии:
- `on-request` (по умолчанию) — модель запрашивает одобрение перед запуском терминальных команд и записью файлов.
- `never` — команды выполняются без остановки на диалог (используется строго в песочницах и headless-скриптах).

> [!IMPORTANT]
> При интерактивной разработке всегда оставляйте режим по умолчанию (`on-request`). Внимательно изучайте предлагаемый diff перед нажатием кнопки одобрения.

## 3. Безопасная работа с Git: быстрое восстановление

Если Codex предложил ошибочный план или diff содержит нежелательные побочные правки, не пытайтесь вручную откатывать каждую строчку. Используйте команды Git:

### Проверка предложенных изменений:
```bash
git diff
```

### Отмена всех незакоммиченных изменений в рабочих файлах:
```bash
git restore .
```

### Очистка новых незакоммиченных временных файлов:
```bash
git clean -fd
```

### Изоляция в Git Worktree
Для крупных или экспериментальных рефакторингов создавайте изолированное рабочее дерево:
```bash
git worktree add ../feature-experiment -b experiment
cd ../feature-experiment
codex "Проведи масштабный рефакторинг API"
```
Если эксперимент не удался, достаточно просто удалить каталог `../feature-experiment`, сохранив основную ветку нетронутой.

## 4. Опасные антипаттерны и запретные зоны

Проектная изоляция требует строгого соблюдения границ:

1. **Никаких правок глобальных конфигов:**
   Модель никогда не должна иметь доступ к изменению `~/.codex/config.toml`, `~/.agents/` или системных файлов ОС. Все конфигурации проекта должны находиться локально в пределах репозитория.
2. **Запрет path traversal (`../`):**
   Пути вроде `../../system/` должны блокироваться на уровне проверок и песочницы.
3. **Сосуществование с другими инструментами:**
   Если на вашем компьютере работают `codex-minimax CLI`, `Codex Desktop` или локальные скрипты, держите их профили строго изолированными. Локальный курс никогда не затрагивает глобальные реестры окружения.

## Практическое упражнение: safety-guard

В каталоге `examples/safety-guard` находится компонент валидации путей доступа. Ваша задача — реализовать строгую функцию проверки, которая гарантирует, что ни один запрашиваемый файл не выходит за пределы рабочего каталога `workspace`.

### Инструкция:
1. Перейдите в каталог упражнения `.learning/workspaces/safety-guard` (или создайте его копию из `examples/safety-guard/starter`).
2. Доработайте файл `guard.py` так, чтобы он возвращал `None` при любой попытке обхода каталога (через `..`, абсолютные пути или тильду).
3. Запустите локальную автономную проверку:
```bash
python scripts/verify.py --exercise safety-guard
```

### Подсказки:
1. Используйте `Path.resolve()` для канонизации пути до проверки.
2. Проверьте отношение предка и потомка с помощью метода `target.relative_to(workspace_root)`.
