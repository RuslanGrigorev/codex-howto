# Постановка задачи с проверяемым результатом

## Чему вы научитесь

Научитесь формулировать запросы (промпты) к Codex CLI 0.160.0 в строгом инженерном стиле, определять однозначные критерии приемки (Definition of Done), явно фиксировать ограничения (границы допустимых изменений, запрет сторонних зависимостей и сети) и использовать детерминированные тесты в качестве объективного арбитра выполнения.

## Что нужно перед началом

1. Изучите основы исследования из урока [Исследование проекта без изменения файлов](inspect.md).
2. Подготовьте изолированное учебное пространство `small-fix`.
3. Понимание разницы между субъективной оценкой качества («сделай красиво») и объективным критерием приёмки («код возврата 0 на независимом тесте»).

## Схема процесса

Анатомия профессионального инженерного промпта:

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. Контекст и наблюдаемая проблема (Context & Defect)       │
│    "В функции apply_discount не обрабатываются границы..."   │
├─────────────────────────────────────────────────────────────┤
│ 2. Ожидаемое поведение (Target Contract)                   │
│    "Для price=100 и discount=0.2 вернуть 80.0;             │
│     при discount < 0 или discount > 1 выбросить ValueError" │
├─────────────────────────────────────────────────────────────┤
│ 3. Границы допустимых изменений (Scope Boundaries)          │
│    "Изменяй ТОЛЬКО файл discount.py. Запрещено трогать      │
│     тесты, добавлять зависимости и обращаться в сеть"       │
├─────────────────────────────────────────────────────────────┤
│ 4. Способ проверки и артефакты (Verification & Deliverables) │
│    "Сначала покажи минимальный diff, затем запусти test.py" │
└─────────────────────────────────────────────────────────────┘
```

## Команды и параметры

Команды передачи структурированных запросов в Codex CLI:

```bash
# Интерактивная передача промпта в TUI
codex

# Пакетная передача через аргумент командной строки
codex exec "Контекст: ... Задача: ... Границы: ... Проверка: ..."

# Передача подробного ТЗ через файл спецификации
codex exec --stdin < task_spec.txt

# Проверка результата выполнения
git diff --stat
python test.py
```

## Разбор примера

Сравним два подхода к постановке одной и той же задачи:

### Плохой промпт (неопределённый):
```text
Сделай расчёт скидки лучше и надёжнее, исправь все баги и оптимизируй код.
```
*Последствия*: модель перепишет функцию, переименует аргументы, установит стороннюю библиотеку для валидации, удалит проверки в тестах и выдаст неконтролируемый diff на 100 строк.

### Качественный инженерный промпт (проверяемый):
```text
Контекст: функция apply_discount в файле discount.py.
Проблема: для price=100 и discount=0.2 возвращается 20.0 вместо 80.0, а при discount=1.5 не генерируется ошибка.
Задача:
1. Исправь формулу на price * (1.0 - discount).
2. Добавь проверку: если price < 0 или discount не в диапазоне [0.0, 1.0], выброси ValueError.
Ограничения:
- Изменяй строго discount.py.
- Не модифицируй test.py и не вводи внешних пакетов.
Артефакты:
- Покажи минимальный diff.
- Запусти независимый тест examples/small-fix/test.py и покажи вывод.
```

## Ограничения и безопасность

1. **Запрет на ослабление тестов**: всегда явно запрещайте модели модифицировать файлы тестов (`test.py`, `*_test.py`). Без этого запрета агент может подогнать утверждения теста под ошибочную реализацию функции.
2. **Запрет скрытых зависимостей**: без явного ограничения агент может попытаться выполнить `pip install` или `npm install`, добавив ненужные внешние пакеты.
3. **Безопасность Git-операций**: не разрешайте модели делать `git push` или автоматически коммитить сырой результат без проверки человеком.

## Ошибки и диагностика

| Симптом | Причина | Способ диагностики и решения |
|---|---|---|
| Модель изменила тесты вместо кода | Отсутствовал запрет на редактирование тестов в промпте. | Откатите тесты через `git checkout test.py` и добавьте в промпт: «Редактировать тесты запрещено». |
| Слишком большой diff (переписана вся функция) | В промпте не было требования минимального diff. | Добавьте требование: «Внеси минимально необходимое исправление (до 5 строк)». |
| Модель не поняла граничные условия | Не были указаны конкретные значения крайних случаев. | Явно укажите входы и выходы для значений `0.0` и `1.0`. |

## Практика

1. Составьте структурированный промпт для исправления функции `apply_discount` по 4-компонентной схеме (Контекст, Поведение, Границы, Проверка).
2. Запишите составленный промпт в файл `task_prompt.txt`.
3. Проверьте свой промпт по чек-листу:
   - Указаны ли точные имена файлов?
   - Есть ли конкретные числовые примеры входа и выхода?
   - Запрещено ли менять тесты?
   - Указана ли команда проверки?

## Самопроверка

Критерии завершения:
1. Вы умеете структурировать запрос по 4 ключевым секциям.
2. В запросе присутствуют явные ограничения безопасности (запрет правки тестов, запрет внешних пакетов).
3. Сформулирован однозначный воспроизводимый критерий завершения задачи.

<details>
<summary>Контрольные вопросы для самопроверки</summary>

- **Вопрос**: Почему формулировка «напиши красивый код» считается ошибочной при работе с AI-агентом?
- **Ответ**: «Красивый код» — это субъективная и неизмеримая оценка, которая часто провоцирует избыточный рефакторинг и нарушение обратной совместимости.
- **Вопрос**: Какой арбитр является надёжным подтверждением успешного исправления?
- **Ответ**: Запуск независимого детерминированного теста с нулевым кодом завершения (`exit code 0`).

</details>
