# Исследование проекта без изменения файлов

## Чему вы научитесь

Научитесь проводить структурированное исследование (code reconnaissance) незнакомого проекта с помощью Codex CLI 0.160.0 в режиме строгого чтения (`read-only`), выявлять архитектурные слои, точки входа и контракты функций без риска случайной модификации файлов, а также проверять утверждения модели по существующим путям в кодовой базе.

## Что нужно перед началом

1. Изучите основы рабочего цикла из урока [Ограниченное исправление: запрос, diff и тест](small-fix.md).
2. Подготовьте изолированное рабочее пространство `small-fix` для безопасного исследования.
3. Понимание разницы между исследовательской сессией (инспекцией) и сессией внесения изменений (имплементацией).

## Схема процесса

Процесс безопасного исследования репозитория состоит из четырёх этапов:

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. Входной барьер безопасности                             │
│    codex --sandbox read-only --ask-for-approval untrusted     │
│    (Любые попытки записи блокируются песочницей ОС)         │
└───────────────────────────────┬─────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────┐
│ 2. Исследовательский промпт                                 │
│    - Запрос структуры каталогов и ключевых файлов           │
│    - Выявление сигнатур функций и граничных условий         │
│    - Явный запрет на генерацию правок и рефакторинг         │
└───────────────────────────────┬─────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────┐
│ 3. Чтение и сопоставление (Read & Cross-Check)              │
│    - Агент использует инструмент read_file                  │
│    - Сверка названных путей и номеров строк человеком       │
└───────────────────────────────┬─────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────┐
│ 4. Формирование архитектурной карты (Project Map)           │
│    - Список точек входа, зависимостей и мест для тестов     │
│    - Фиксация статуса: git diff пуст (изменений нет)        │
└─────────────────────────────────────────────────────────────┘
```

## Команды и параметры

Команды запуска сессии безопасного исследования:

```bash
# Подготовка изолированного рабочего пространства
python scripts/verify.py --prepare small-fix

# Запуск Codex CLI в режиме строгого чтения
codex -C .learning/workspaces/small-fix --sandbox read-only --ask-for-approval untrusted

# Быстрое неинтерактивное исследование через exec
codex exec --sandbox read-only "Проанализируй discount.py и перечисли граничные условия"

# Проверка того, что файлы на диске не были изменены
git status --short
```

Ключевые параметры:
- `-C <path>`: смена рабочего каталога на целевую папку исследования.
- `--sandbox read-only`: блокировка любых файловых модификаций.

## Разбор примера

Пример формулирования качественного исследовательского запроса:

```text
Исследуй кодовую базу в текущем каталоге. Не изменяй файлы.
Сформируй отчёт из 4 пунктов:
1. Точка входа и основные функции.
2. Принимаемые аргументы и их ожидаемые типы.
3. Граничные случаи, требующие тестирования (крайние значения, исключения).
4. Наличие тестов в текущем каталоге.
Для каждого утверждения обязательно укажи имя файла и номера строк.
```

Наблюдаемый отчёт агента:
```text
1. Основная функция: apply_discount(price, discount) в файле discount.py (строка 1).
2. Аргументы: price (число), discount (доля от 0.0 до 1.0).
3. Граничные условия: discount = 0.0, discount = 1.0, отрицательная цена, discount < 0 или > 1.
4. Тесты: в текущем каталоге тесты отсутствуют (тест test.py расположен во внешней директории курса).
```

## Ограничения и безопасность

1. **Текстовое обещание не заменяет песочницу**: фраза в промпте «не меняй файлы» является лишь инструкцией модели. Гарантию неизменяемости даёт только флаг `--sandbox read-only`, применяемый на уровне ядра CLI.
2. **Проверка галлюцинаций путей**: модели иногда придумывают правдоподобные пути к файлам конфигураций (например, `settings.json`, которого нет в проекте). Всегда проверяйте существование указанных файлов на диске.
3. **Не смешивайте исследование и правку**: не поддавайтесь соблазну сразу исправить найденную ошибку в исследовательской сессии. Сначала зафиксируйте план, а затем начните новую сессию с соответствующими правами записи.

## Ошибки и диагностика

| Симптом | Причина | Способ диагностики и решения |
|---|---|---|
| Модель пытается модифицировать файл во время исследования | Модель посчитала задачу «исправлением ошибки». | Принудительно используйте `--sandbox read-only`. CLI заблокирует попытку записи. |
| Модель ссылается на файл, отсутствующий в репозитории | Галлюцинация на основе общих знаний о фреймворке. | Задайте уточняющий вопрос: «Укажи точный путь к этому файлу в дереве проекта». |
| Отчёт перегружен длинными цитатами кода | Не задан лимит на размер ответа. | Добавьте в промпт ограничение: «Кратко, не более 5 строк на пункт». |

## Практика

1. Подготовьте учебное пространство:
   ```bash
   python scripts/verify.py --prepare small-fix
   ```
2. Откройте сессию исследования в режиме `read-only` или изучите исходный файл `discount.py`:
   ```bash
   cat .learning/workspaces/small-fix/discount.py
   ```
3. Составьте краткую карту из 3 пунктов: назначение функции, аргументы, дефект в коде.
4. Убедитесь с помощью `git status`, что ни один файл не был случайно изменён.

<details>
<summary>Подсказка к выполнению практики</summary>

Хороший исследовательский анализ разделяет факты и гипотезы. Факт: `discount.py` возвращает `price * discount`. Гипотеза: разработчик перепутал вычисление размера скидки с вычислением цены с учётом скидки `price * (1 - discount)`.

</details>

## Самопроверка

Критерии завершения:
1. Вы понимаете, почему исследование необходимо проводить в режиме `--sandbox read-only`.
2. Вы умеете проверять отсутствие изменений в репозитории после исследования.
3. Сформирована точная карта дефекта без модификации исходного кода.

<details>
<summary>Контрольные вопросы для самопроверки</summary>

- **Вопрос**: Зачем запускать отдельную сессию только для чтения перед внесением правок?
- **Ответ**: Это позволяет полностью понять контекст задачи, зависимости и критерии тестов без риска внесения случайных разрушительных изменений.
- **Вопрос**: Что произойдёт, если модель попытается вызвать `edit_file` в режиме `--sandbox read-only`?
- **Ответ**: Песочница ядра CLI мгновенно отклонит вызов инструмента с ошибкой доступа, сохранив файл неизменным.

</details>
