# Планирование в /plan: от требований к шагам

## Чему вы научитесь

Научитесь использовать встроенный режим планирования `/plan` в Codex CLI 0.160.0 для декомпозиции сложных многоэтапных инженерных задач на атомарные шаги с критериями верификации, анализировать план до начала редактирования кода, исключать скрытые опасные действия и плавно переходить от этапа согласования архитектуры к этапу исполнения.

## Что нужно перед началом

1. Изучите уроки [Исследование проекта без изменения файлов](inspect.md) и [Постановка задачи с проверяемым результатом](prompt.md).
2. Подготовьте задачу средней сложности (например, добавление валидации и тестов в несколько модулей).
3. Понимание различий между режимом планирования (`/plan`) и режимом автономного исполнения цели (`/goal`).

## Схема процесса

Двухфазный рабочий процесс «Сначала спланируй, затем реализуй»:

```text
Фаза 1: Режим планирования (/plan)
┌─────────────────────────────────────────────────────────────┐
│ Ввод пользователя: /plan "Задача..."                        │
│ ├── Модель анализирует требования                           │
│ ├── Формирует структуру: Шаг -> Вход -> Результат -> Тест   │
│ └── Файлы на диске НЕ изменяются (Strict Read-Only)         │
└──────────────────────────────┬──────────────────────────────┘
                               │
┌──────────────────────────────▼─────────────────────────────┐
│ Ревизия плана человеком (Review Checkpoint)                 │
│ ├── Удаление лишних шагов и нежелательных зависимостей     │
│ └── Утверждение финального списка шагов                     │
└──────────────────────────────┬──────────────────────────────┘
                               │
Фаза 2: Режим исполнения (Execution)
┌──────────────────────────────▼─────────────────────────────┐
│ Последовательная реализация утверждённых шагов              │
│ ├── Шаг 1: Правка файла -> Проверка тестом                  │
│ ├── Шаг 2: Правка следующего файла -> Проверка тестом       │
│ └── Финальный diff и проверка регрессий                     │
└─────────────────────────────────────────────────────────────┘
```

## Команды и параметры

Команды управления планированием в сессии TUI:

```text
/plan "Текст задачи"     # Включение режима планирования с формулировкой цели
/plan                    # Переключение текущей сессии в режим планирования
/plan review             # Инспекция текущего утверждённого плана
/plan edit               # Ручная корректировка пунктов плана в редакторе
```

Флаги CLI для неинтерактивного формирования плана:

```bash
# Генерация плана без изменения файлов репозитория
codex exec --sandbox read-only "/plan Сформируй план рефакторинга auth.py"
```

## Разбор примера

Рассмотрим формирование плана для задачи ограниченного исправления `small-fix`:

1. Пользователь вводит команду в TUI:
   ```text
   /plan Исправь расчёт скидки в discount.py:
   1. Сначала перечисли граничные случаи.
   2. Сформируй минимальное исправление.
   3. Проверь независимый тест examples/small-fix/test.py.
   Не изменяй файлы на этапе планирования.
   ```
2. Модель формирует структурированный план:
   ```text
   ### План исправления:
   - [ ] Шаг 1: Анализ граничных условий в discount.py (price < 0, discount not in [0.0, 1.0]).
   - [ ] Шаг 2: Разработка точечного diff для функции apply_discount (добавление валидации и исправление формулы).
   - [ ] Шаг 3: Прогон независимого теста examples/small-fix/test.py.
   - [ ] Шаг 4: Проверка отсутствия изменений в тестах через git diff.
   ```
3. Пользователь видит все шаги, одобряет их и переходит к исполнению.

## Ограничения и безопасность

1. **План — это не выполнение**: генерация красивого плана со статусами `[ ]` не означает, что код был написан или тесты прошли. Это исключительно декларация намерений.
2. **Исключение нежелательных шагов**: если модель включила в план установку внешних пакетов (`pip install ...`) или рефакторинг не связанных файлов, обязательно удалите эти пункты до запуска реализации.
3. **Безопасность песочницы на этапе плана**: на этапе планирования сессия должна оставаться в безопасном режиме чтения, чтобы предотвратить случайное применение непроверенных промежуточных вариантов.

## Ошибки и диагностика

| Симптом | Причина | Способ диагностики и решения |
|---|---|---|
| Команда `/plan` не распознаётся оболочкой | Команда введена в bash/powershell вместо TUI сессии Codex. | Запустите сначала `codex`, а команду `/plan` вводите внутри сессии. |
| План слишком общий («1. Изучить, 2. Сделать, 3. Проверить») | Недостаточная детализация исходного запроса. | Попросите модель: «Детализируй каждый шаг с указанием конкретных файлов и критериев проверки». |
| Модель сразу начала менять код вместо составления плана | Команда `/plan` была опущена в начале запроса. | Прервите сессию через `Ctrl+C` и начните заново с явного вызова `/plan`. |

## Практика

1. Откройте сессию Codex в изолированной копии `small-fix`.
2. Введите команду `/plan` с описанием задачи валидации скидки.
3. Оцените сгенерированный план:
   - Содержит ли он конкретные шаги с именами файлов?
   - Указана ли команда запуска теста?
   - Нет ли в плане лишних действий (установка сторонних библиотек, изменение `test.py`)?
4. Скорректируйте план при наличии лишних пунктов.

<details>
<summary>Подсказка к выполнению практики</summary>

Ключевой признак качественного шага плана — проверяемость. Пункт «Оптимизировать производительность» непроверяем. Пункт «Запустить test.py и убедиться в коде возврата 0» — абсолютно проверяем.

## Самопроверка

Критерии завершения:
1. Вы понимаете назначение и поведение команды `/plan`.
2. Вы умеете анализировать сгенерированный план на наличие скрытых опасных операций.
3. Вы отличаете этап планирования от этапа непосредственного внесения изменений.

<details>
<summary>Контрольные вопросы для самопроверки</summary>

- **Вопрос**: Изменяет ли команда `/plan` файлы на диске?
- **Ответ**: Нет, режим `/plan` предназначен строго для анализа и структурирования шагов без модификации файлов репозитория.
- **Вопрос**: В чём отличие `/plan` от `/goal`?
- **Ответ**: `/plan` создаёт пошаговый маршрут для согласования с человеком, а `/goal` запускает сквозное автономное выполнение до достижения долгосрочной цели.

</details>
