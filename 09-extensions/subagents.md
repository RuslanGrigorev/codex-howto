# Субагенты: роли, границы и проверка результата

## Чему вы научитесь

- Проектировать роли специализированных субагентов (Subagents) для Codex CLI.
- Создавать файлы конфигурации субагентов в формате `.codex/agents/*.toml`.
- Разграничивать полномочия: изоляция ролей исследователя (`read-only`), разработчика (`workspace-write`) и ревьюера.
- Предотвращать конфликты параллельной записи в одни и те же файлы и объединять результаты работы.

## Что нужно перед началом

- Знакомство с архитектурой делегации из урока [Архитектура субагентов: разделение ролей и изоляция](agent-design.md) (схема D10).
- Каталог `.codex/agents/` в проекте.
- Установленный Codex CLI 0.160.0.

## Схема процесса

Координация и разделение полномочий субагентов:

```
┌────────────────────────────────────────────────────────┐
│             Ведущий агент (Orchestrator)               │
│          Анализирует задачу, составляет план           │
└───────────────────────────┬────────────────────────────┘
                            │
              ┌─────────────┴─────────────┐
              │ Делегация подзадачи       │
              ▼                           ▼
┌───────────────────────────┐ ┌───────────────────────────┐
│ Субагент: explorer        │ │ Субагент: reviewer        │
│ Роль: Анализ кода и тестов│ │ Роль: Аудит безопасности  │
│ Песочница: read-only      │ │ Песочница: read-only      │
│ Доступ к записи: ЗАПРЕЩЕН │ │ Доступ к записи: ЗАПРЕЩЕН │
└─────────────┬─────────────┘ └─────────────┬─────────────┘
              │                             │
              └─────────────┬───────────────┘
                            │ Структурированные отчеты
                            ▼
┌────────────────────────────────────────────────────────┐
│ Субагент: implementer                                  │
│ Роль: Прицельное внесение правок                       │
│ Песочница: workspace-write (только целевые файлы)      │
└────────────────────────────────────────────────────────┘
```

## Команды и параметры

Команды управления субагентами в сессии:

```text
# Просмотр зарегистрированных ролей субагентов в сессии
/subagents

# Делегация подзадачи конкретной роли
@reviewer Проверь diff последних изменений на утечки памяти
```

Пример описания субагента в `.codex/agents/reviewer.toml`:

```toml
name = "code-reviewer"
description = "Эксперт по безопасности и поиску регрессий в коде."
model = "gpt-4o"

[sandbox]
mode = "read-only"
deny_network = true

[developer_instructions]
prompt = """
Ты — специализированный ревьюер кода.
Твоя задача — анализировать diff и искать потенциальные баги, утечки ресурсов и уязвимости.
Никогда не пытайся изменять файлы проекта: твоя песочница работает строго в режиме чтения.
Формируй отчет со списком замечаний и оценкой критичности (P0-P3).
"""
```

## Разбор примера

Рассмотрим процесс решения комплексной задачи рефакторинга:

1. Ведущий агент получает задачу: «Оптимизировать запросы к базе данных в модуле `db/queries.py`».
2. Ведущий агент запускает субагента `explorer` (в режиме `read-only`), чтобы изучить структуру индексов и существующие тесты.
3. Получив отчет от `explorer`, ведущий агент передает задачу модификации субагенту `implementer`.
4. После внесения правок ведущий агент вызывает субагента `reviewer`:
   - `reviewer` запускает `pytest` и анализирует измененные строки.
   - Обнаруживает потенциальный SQL Injection в динамическом формировании фильтра.
5. Ведущий агент возвращает задачу `implementer` на доработку с учетом замечаний `reviewer`.
6. Итоговый код безопасен и покрыт тестами.

## Ограничения и безопасность

- Назначение правильного режима песочницы для каждой роли критично: исследовательские субагенты должны иметь строгий режим `read-only`, чтобы исключить случайные сайд-эффекты.
- Не запускайте нескольких субагентов с правами на запись одновременно над одним рабочим деревом файлов: это приводит к race conditions и порче кода.
- Субагенты наследуют ограничения глобальных правил проекта `AGENTS.md`.

## Типовые ошибки

1. **Выдача широких прав всем ролям**: назначение `workspace-write` субагенту-аналитику или ревьюеру.
2. **Параллельная несинхронизированная запись**: попытка двух агентов одновременно переписать один и тот же модуль.
3. **Безоговорочное доверие галлюцинациям субагента**: принятие ведущим агентом неподтвержденных выводов без запуска валидационных тестов.

## Практика

1. Создайте файл конфигурации субагента `.codex/agents/reviewer.toml` в режиме `read-only`.
2. Проверьте регистрацию новой роли через команду `/subagents`.
3. Поручите субагенту провести анализ тестового файла и сформировать перечень замечаний.
4. Убедитесь, что субагент не может изменить файлы на диске даже при явной попытке вызова инструмента записи.

## Самопроверка

<details>
<summary>Подсказка и критерии самопроверки</summary>

- Убедитесь, что команда `/subagents` отображает новую роль и корректный профиль песочницы (`read-only`).
- Проверьте, что попытка субагента модифицировать файл блокируется с ошибкой нарушения песочницы.
- Критерий успешности: субагент успешно выполняет анализ и выдает структурированные рекомендации без изменения файлов проекта.

</details>
