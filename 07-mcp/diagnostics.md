# Диагностика MCP: процесс, транспорт и авторизация

## Чему вы научитесь

- Локализовать сбои серверов Model Context Protocol по 4 уровням: процесс ОС, транспорт JSON-RPC, схема инструментов и бизнес-логика.
- Диагностировать типичную проблему stdio-серверов: загрязнение канала stdout отладочным выводом.
- Использовать команды `codex mcp list` и журнал `stderr` для выявления причин падения процессов.
- Безопасно проверять сетевые и авторизационные сбои без утечки токенов в лог-файлы.

## Что нужно перед началом

- Понимание протокола MCP и структуры stdio/SSE транспортов.
- Локальный скрипт сервера на Python или Node.js.
- Установленный Codex CLI 0.160.0.

## Схема процесса

Иерархическая матрица диагностики сбоев MCP:

```
┌────────────────────────────────────────────────────────┐
│  Уровень 1: Процесс ОС (OS Process Execution)          │
│  Симптом: "command not found" / "spawn ENOENT"         │
│  Действие: Проверить путь к python/node, PATH, права    │
└───────────────────────────┬────────────────────────────┘
                            │ Процесс стартовал
                            ▼
┌────────────────────────────────────────────────────────┐
│  Уровень 2: Транспорт JSON-RPC (Framing & Parsing)     │
│  Симптом: "JSON parse error" / "Unexpected token"      │
│  Действие: Убедиться, что print() пишет в stderr!      │
└───────────────────────────┬────────────────────────────┘
                            │ Протокол согласован
                            ▼
┌────────────────────────────────────────────────────────┐
│  Уровень 3: Схема и инструменты (Schema Discovery)     │
│  Симптом: "Tool not found" / "Schema validation failed"│
│  Действие: Проверить обработчик tools/list и types     │
└───────────────────────────┬────────────────────────────┘
                            │ Инструмент вызван
                            ▼
┌────────────────────────────────────────────────────────┐
│  Уровень 4: Бизнес-логика инструмента (Tool Execution) │
│  Симптом: "FileNotFound" / "Database error 500"        │
│  Действие: Проверить аргументы и права песочницы       │
└────────────────────────────────────────────────────────┘
```

## Команды и параметры

Команды диагностики MCP-серверов:

```bash
# Просмотр всех зарегистрированных серверов и статусов соединения
codex mcp list

# Проверка детальной информации и схемы инструментов
codex mcp inspect server-name

# Ручной запуск stdio-сервера в изолированном терминале для проверки stderr
python -u -m my_mcp_server --root ./data
```

Пример корректного логирования в коде сервера:

```python
import sys

# ПРАВИЛЬНО: диагностика пишется исключительно в sys.stderr
sys.stderr.write("DEBUG: Server initialized successfully\n")
sys.stderr.flush()

# НЕПРАВИЛЬНО: print() без file=sys.stderr сломает JSON-RPC парсер в stdout!
# print("DEBUG: This will crash the client JSON parser!")
```

## Разбор примера

Рассмотрим диагностику упавшего сервера:

1. Выполняем `codex mcp list`: сервер `analyzer` помечен статусом `failed: exit code 1`.
2. Анализируем причину:
   - Запускаем команду сервера вручную в терминале:
     ```bash
     python -m analyzer_mcp
     ```
   - Получаем вывод: `ModuleNotFoundError: No module named 'mcp'`.
   - Проблема на Уровне 1: в активном виртуальном окружении не установлен пакет SDK.
3. Активируем окружение или указываем абсолютный путь к интерпретатору в `.codex/config.toml`:
   ```toml
   [mcp_servers.analyzer]
   command = "/home/user/venv/bin/python"
   args = ["-m", "analyzer_mcp"]
   ```
4. После обновления перезапускаем `codex mcp list`: статус сменяется на `running`.

## Ограничения и безопасность

- В режиме stdio канал `stdout` зарезервирован строго под протокольные сообщения JSON-RPC: любая сторонняя строка или предупреждение библиотеки нарушит десериализацию.
- Никогда не выводите токены авторизации (Bearer-токены, API-ключи) в поток `stderr` или отладочные дампы.
- Если сервер аварийно завершается, Codex CLI изолирует сбой и продолжает работу сессии без краша основного процесса.

## Типовые ошибки

1. **Загрязнение stdout**: использование стандартного `print()` для отладки вместо `sys.stderr.write()`.
2. **Относительные пути к бинарникам**: использование команды `python` вместо указания виртуального окружения, из-за чего берется системный интерпретатор без нужных библиотек.
3. **Игнорирование буферизации**: отсутствие вызова `.flush()` при отправке JSON-RPC строк в stdout, приводящее к зависанию ожидания ответа.

## Практика

1. Создайте минимальный тестовый MCP-сервер на Python, записывающий отладку в `sys.stderr`.
2. Зарегистрируйте его в тестовом файле конфигурации и проверьте вывод команды `codex mcp list`.
3. Намеренно добавьте в код сервера вызов `print("Corrupted output")` в поток `stdout` и зафиксируйте ошибку парсинга транспорта в CLI.
4. Исправьте ошибку перенаправлением отладки в `stderr` и подтвердите восстановление работоспособности.

## Самопроверка

<summary>Подсказка и критерии самопроверки</summary>

- Убедитесь, что `codex mcp list` показывает статус сервера `ready` или `running`.
- Проверьте, что в потоке `stdout` выводятся только валидные JSON-RPC строки с разделителем `\n`.
- Критерий успешности: сервер корректно отвечает на вызовы `tools/list` и `tools/call` без ошибок десериализации.
