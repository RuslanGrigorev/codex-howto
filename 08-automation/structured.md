# Итог по JSON Schema и продолжение exec

## Чему вы научитесь

- Использовать флаг `--output-schema` для получения строго структурированных JSON-ответов от Codex CLI.
- Различать поток промежуточных событий JSONL (`--json`) и финальный структурированный артефакт (`-o result.json`).
- Возобновлять пакетное выполнение неинтерактивных задач с помощью команды `codex exec resume`.
- Валидировать сгенерированный JSON независимыми схемами JSON Schema (Draft 7 / 2020-12).

## Что нужно перед началом

- Понимание основ JSON Schema (типы данных, обязательные поля `required`, свойства `properties`).
- Базовый опыт работы с `codex exec` из предыдущих уроков.
- Установленный Codex CLI 0.160.0.

## Команды и параметры

Параметры структурированного вывода и продолжения сессий:

```bash
# Генерация структурированного JSON ответа в файл по указанной схеме
codex exec --sandbox read-only --output-schema schemas/result.schema.json -o result.json "Проанализируй проект и составь сводку"

# Запуск одноразовой сессии без сохранения метаданных на диск
codex exec --ephemeral "Выполни быструю проверку синтаксиса"

# Возобновление неинтерактивной сессии по идентификатору
codex exec resume <SESSION_ID> "Продолжи предыдущий анализ и проверь зависимости"
```

Пример схемы `schemas/result.schema.json`:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "project_name": { "type": "string" },
    "files_analyzed": { "type": "integer", "minimum": 0 },
    "has_vulnerabilities": { "type": "boolean" },
    "summary": { "type": "string" }
  },
  "required": ["project_name", "files_analyzed", "has_vulnerabilities", "summary"],
  "additionalProperties": false
}
```

## Разбор примера

Рассмотрим автоматическую генерацию отчета для CI/CD конвейера:

1. Создаем файл схемы `result.schema.json` с требованием предоставить статус безопасности.
2. Запускаем команду:
   ```bash
   codex exec --sandbox read-only --output-schema result.schema.json -o audit.json "Проверь зависимости в requirements.txt"
   ```
3. Codex задействует механизм Structured Outputs языковой модели:
   Файл `audit.json` гарантированно содержит валидный JSON без лишнего сопроводительного текста («Вот ваш JSON:...»).
4. Содержимое `audit.json`:
   ```json
   {
     "project_name": "codex-howto",
     "files_analyzed": 1,
     "has_vulnerabilities": false,
     "summary": "Все зафиксированные зависимости актуальны и безопасны."
   }
   ```
5. Внешний скрипт на Python считывает `audit.json` и принимает решение о прохождении шага сборки.

## Ограничения и безопасность

- Флаг `--ephemeral` отключает локальное сохранение сессии в `~/.codex/sessions/`, однако он **не отзывает** уже переданные провайдеру данные через сетевой API.
- Структурная валидность JSON не гарантирует фактическую истинность фактов: модель может вернуть валидный `has_vulnerabilities: false`, пропустив реальный дефект кода.
- Всегда перепроверяйте утверждения модели независимыми тестами и линтерами.

## Типовые ошибки

1. **Смешение флагов**: одновременное ожидание структурированного JSON из stdout при включенном `--json` (который выводит поток JSONL).
2. **Некорректная схема**: использование расширений JSON Schema, не поддерживаемых движком Structured Outputs модели.
3. **Запись в корень без прав**: указание выходного файла `-o /root/result.json` при активной песочнице `read-only`.

## Практика

1. Подготовьте файл JSON Schema с описанием полей статуса проверки кода.
2. Запустите `codex exec` с указанием вашей схемы и сформируйте выходной файл `result.json`.
3. Напишите проверочный скрипт на Python с использованием библиотеки `jsonschema` и убедитесь в соответствии результата схеме.
4. Намеренно повредите выходной файл (удалите обязательное поле) и проверьте реакцию валидатора.
