# Повторный запуск и продолжение автоматизированной задачи

## Чему вы научитесь

- Проектировать идемпотентные и безопасные механизмы повторных запусков (Retry Policies) для Codex CLI.
- Различать старт новой сессии и продолжение прерванной задачи через `codex exec resume`.
- Предотвращать дублирование деструктивных действий (повторное создание веток, двойная отправка API-запросов).
- Реализовывать стратегию экспоненциальной задержки (Exponential Backoff with Jitter) при сетевых сбоях.

## Что нужно перед началом

- Понимание работы команды `codex exec` и формата событий JSONL из уроков этого модуля.
- Базовые знания о принципах идемпотентности в распределенных системах.
- Установленный Codex CLI 0.160.0.

## Схема процесса

Безопасный цикл повтора с контролем идемпотентности:

```
[Старт автоматизированной задачи: codex exec ...]
                        │
                        ▼
            [Возник сбой / Ошибка выполнения]
                        │
                        ▼
┌────────────────────────────────────────────────────────┐
│             Анализ характера ошибки (Triage)           │
├────────────────────────────────────────────────────────┤
│ Временный сетевой сбой (429 / 503)? ──> Retry Backoff  │
│ Ошибка логики / Синтаксиса кода?    ──> Стоп, аудит    │
│ Ошибка прав песочницы?              ──> Стоп, фатально │
└───────────────────────┬────────────────────────────────┘
                        │ Допустим повтор
                        ▼
┌────────────────────────────────────────────────────────┐
│       Проверка состояния перед повтором (Git/FS)       │
├────────────────────────────────────────────────────────┤
│ Были ли частично применены файлы на диске?             │
│ ДА  ──> codex exec resume <ID> "Продолжи с шага X"     │
│ НЕТ ──> codex exec "Запусти задачу заново"             │
└────────────────────────────────────────────────────────┘
```

## Команды и параметры

Команды управления повторами и возобновлением:

```bash
# Просмотр параметров повторного запуска
codex exec resume --help

# Возобновление упавшей сессии с указанием контекста ошибки
codex exec resume 3b8c19ef-.. --sandbox workspace-write "Предыдущий запуск прервался по таймауту. Проверь уже созданные файлы и заверши сборку."

# Запуск с ограничением общего времени выполнения для предотвращения зависаний
timeout 300 codex exec --json "Выполни миграцию"
```

Пример параметров политики повторов в конфигурационном файле:

```toml
[automation.retry]
max_attempts = 3
initial_backoff_ms = 1000
max_backoff_ms = 30000
retry_on_status = [429, 500, 502, 503]
```

## Разбор примера

Рассмотрим процесс обработки сбоя из-за лимита запросов (Rate Limit 429):

1. Скрипт автоматизации запускает задачу через `codex exec --json`.
2. На шаге 3 генерации процесс возвращает событие `turn.failed` с ошибкой:
   `{"code": "rate_limit_exceeded", "message": "Requests per min limit reached"}`.
3. Скрипт не начинает слепой запуск с нуля:
   - Сохраняет `session_id`.
   - Проверяет `git status`: файлы ещё не затронуты.
   - Выдерживает экспоненциальную паузу (например, 15 секунд).
4. Запускает продолжение:
   ```bash
   codex exec resume <session_id>
   ```
5. Сессия успешно возобновляется с точки останова без потери контекста предыдущих размышлений модели.

## Ограничения и безопасность

- Никогда не настраивайте бесконечные циклы повторов (`while true; do codex exec ...; done`): это приводит к лавинообразному расходу токенов и блокировке учетной записи.
- Если сессия успела внести частичные изменения в файлы, слепой повторный запуск новой сессии приведет к конфликтам и испорченному коду.
- Повторные вызовы внешних инструментов (например, создание тикетов в трекере) должны сопровождаться проверкой ключей идемпотентности.

## Типовые ошибки

1. **Слепой повтор всего сценария**: запуск новой сессии вместо `codex exec resume`, когда половина работы уже сделана.
2. **Игнорирование фатальных ошибок**: повторные попытки при ошибке `PermissionDenied` или отсутствии файла, которые никогда не решатся сами собой.
3. **Отсутствие задержки (No Backoff)**: немедленный спам запросами к API после получения ошибки 429.

## Практика

1. Смоделируйте сценарий сбоя в пакетной обработке (например, передайте команду, завершающуюся ошибкой).
2. Зафиксируйте полученный идентификатор сессии.
3. Сформируйте команду `codex exec resume`, передающую агенту инструкцию по исправлению возникшей ошибки.
4. Убедитесь, что продолженная сессия использует контекст предыдущей попытки.

## Самопроверка

<details>
<summary>Подсказка и критерии самопроверки</summary>

- Убедитесь, что логика повтора проверяет код ошибки и не перезапускает заведомо неисправимые фатальные сбои.
- Проверьте, что при повторном запуске через `exec resume` агент видит предыдущие шаги и не дублирует уже сделанные правки.
- Критерий успешности: система восстанавливается после временных сетевых сбоев без повреждения состояния репозитория.
